# Этап 6 — кухня и склад

## Производственный контур

Одна кухня работает с агрегированным списком, а не с экраном клиентских заказов. Идентичность строки определяется хешем блюда/add-on, версии рецепта, размера порции, modifications и индивидуальных ограничений. Поэтому взрослый/детский размер, исключённый ингредиент, платная добавка или аллергенная маркировка никогда не сливаются в неразличимую строку.

Ревизии имеют виды `FORECAST`, `FINAL`, `DELTA` и состояния `DRAFT → LOCKED → IN_PROGRESS → COMPLETED`. Forecast не резервирует и не списывает склад. FINAL фиксирует plan после lock и создаёт резервы/packing tasks. Повторная фиксация до производства создаёт DELTA: новая потребность сравнивается с суммой активных резервов даты, включая ингредиенты, исчезнувшие из новой версии. Завершённую production нельзя тихо переписать.

Подтверждение производства выполняется одной транзакцией под advisory locks ингредиентов: рассчитывается факт по recipe snapshot, проверяется остаток, создаётся ровно одно движение `PRODUCTION`, снимаются резервы и фиксируется `ProductionRun`. `revision_id` и idempotency key уникальны, поэтому повторный клик или повтор после рестарта не списывает сырьё второй раз.

## Упаковка

Packing task создаётся на household fulfillment, а позиции — на member/guest и конкретную строку блюда/add-on. В snapshot этикетки попадают только имя/идентификатор участника, дата, номер заказа, состав комплекта и необходимая для предотвращения ошибки индивидуальная маркировка. Анкета целиком и QR не печатаются.

Задача проходит `PENDING → IN_PROGRESS → COMPLETE`; позиции — `PENDING/PACKED/MISSING`. Команда завершения проверяет все позиции в транзакции. При любой неполной позиции возвращается `PACKING_INCOMPLETE`, а daily fulfillment не переходит в `READY` и delivery job не создаётся.

## Склад и стоимость

- Канонические единицы: `g` для массы, `ml` для объёма, `piece` для штук. `kg/l` нормализуются; масса ↔ объём разрешены только при положительной density конкретного ингредиента.
- `on_hand` и `reserved` разделены. Доступный остаток равен `on_hand - reserved`; PostgreSQL запрещает отрицательные значения и резерв выше факта.
- Приёмка purchase создаёт `PURCHASE` и пересчитывает weighted average: `(старый остаток × старая цена + приход × цена прихода) / новый остаток`.
- `PRODUCTION`, `WASTE`, `CORRECTION`, `RETURN`, `TRANSFER` создают неизменяемые движения с actor/reason/reference. Клиентский refund сам по себе не создаёт складской `RETURN`.
- Фактическое производство списывает по средней цене, сохранённой в движении. Recipe snapshot и cost snapshot позволяют воспроизвести стоимость после изменения справочников.
- Cost report складывает production movements и `waste_entries`. Связанное с waste движение повторно не суммируется. Revenue берётся по датам успешных payments/refunds; отчёт показывает food cost, gross margin и процент food cost, явно отделяя предварительные оценки от факта.

## Печать

`PrintDocument` хранит неизменяемый content snapshot, HTML preview, page size, SHA-256, автора, время и связь с исходной/повторной печатью. Поддержаны A4, 100×150 мм и 58×40 мм. PDF формируется встроенным Unicode-шрифтом; это переносимый layout, а не заявление о совместимости с неизвестной моделью принтера.

## Staff API

- `GET/POST /api/v1/staff/kitchen/production*` — ревизии, факт и подтверждение;
- `POST/PUT /api/v1/staff/kitchen/packing*` — начало, позиции, завершение;
- `GET /inventory`, `GET/POST /suppliers`, `GET/POST /purchases`, `POST /purchases/items/:id/receive`;
- `POST /inventory/waste`, `POST /inventory/movements`, `GET /costs`;
- `POST /print`, `GET /print/history`, `GET /print/:id/preview|pdf`.

Все endpoints защищены `kitchen.manage` либо `inventory.manage`. Изменяемые строки используют version/optimistic concurrency; финансовые и складские ограничения повторно проверяются backend и PostgreSQL.

## Проверка

`scripts/verify-stage6-e2e.sh` проверяет реальные PostgreSQL/API операции: два несовместимых варианта остаются разными строками; повторное production confirmation возвращает тот же run и одно движение; повторный waste создаёт одну запись и один cost; неполную упаковку нельзя завершить; PDF endpoint возвращает настоящий `%PDF`.
