## 4. Технологическая архитектура

Используй базовую архитектуру из ТЗ:

| Слой | Реализация |
| --- | --- |
| Mobile | Flutter + Dart, единая кодовая база Android/iOS |
| Состояние mobile | Riverpod как базовый технический выбор; не смешивай несколько конкурирующих систем управления состоянием |
| Mobile navigation | `go_router`, проверка auth/onboarding, deep links |
| Mobile data | Типизированные DTO, repositories/services, HTTP-клиент с обработкой auth и ошибок; secure storage для чувствительных токенов |
| Admin | Next.js + React + TypeScript, типизированный API-клиент, формы и таблицы |
| Backend | NestJS + TypeScript, модульный монолит |
| База и ORM | PostgreSQL + Prisma, миграции, ограничения целостности, транзакции |
| Redis и jobs | Redis + BullMQ, безопасные повторные jobs, locks там, где нужны |
| Realtime | WebSocket/Socket.IO для поддержки и обновлений состояния |
| Push | Firebase Cloud Messaging, архитектура с последующей iOS/APNs-конфигурацией |
| Файлы | S3-compatible storage; для local — совместимый локальный сервис |
| Доставка | DeliveryProvider и отдельный Yandex-адаптер |
| Контейнеры | Docker / Docker Compose |
| Reverse proxy | Nginx |
| CI | GitHub Actions |
| Размещение после local | VPS PS.kz; конфигурация должна быть переносимой и не зависеть от выдуманного домена/IP |

В Flutter раздели presentation, application/domain при необходимости и data. Не размещай бизнес-расчёты в widgets. Организуй код по функциональным областям, выдели общие theme, networking, localization, errors и components. Backend остаётся источником истины для цены, прав, cut-off, аллергенов, баланса, статусов и доступности операций. Клиентские проверки улучшают UX, но не заменяют серверные.

В качестве ориентира используй [официальные рекомендации по архитектуре Flutter](https://docs.flutter.dev/app-architecture/recommendations). Конкретные библиотеки выбирай с проверкой их актуальной документации и поддержки обеих мобильных платформ.

Не вводи микросервисы, Kubernetes, отдельную event-streaming платформу и множество инфраструктурных сервисов ради предполагаемого будущего масштаба. Backend API и worker могут быть отдельными процессами одного приложения и использовать общие доменные модули.

## 5. Продуктовые границы, которые нельзя менять

JANTOK Food — персонализированная месячная подписка на ежедневное питание в Астане. Каждое утро семья получает одну доставку с завтраком, обедом и ужином для каждого питающегося участника. Главный пользовательский сценарий — готовый рацион по анкете, а изменения блюд и дополнительные покупки дополняют подписку.

Обязательные ограничения:

- Один город: Астана, Казахстан. Посёлки и адреса за границами обслуживаемой зоны не обслуживаются.
- Одна кухня. Первая аудитория примерно 50–100 клиентов, ориентир мощности 100–200 клиентов.
- Широкая аудитория и средний ценовой сегмент, включая семьи с детьми.
- Один основной продукт — месячная подписка на 30 оплаченных дней питания.
- Работа 7 дней в неделю, включая воскресенье.
- Три приёма пищи на человека в одной утренней доставке.
- Нет отдельных основных тарифов Basic/Premium/Sport. Индивидуальность определяется анкетой и pricing/nutrition rules.
- Нет самостоятельной покупки основного питания без подписки; гости и add-ons доступны внутри действующей подписки.
- Только заранее предусмотренные блюда и доступные альтернативы. Нет заказа произвольного блюда «приготовьте что угодно».
- Все питание halal; это ограничение каталога, ингредиентов и доступных вариантов.
- Все три языка: `kk`, `ru`, `en`. Казахский — основной язык бренда.

Реклама планируется сразу после запуска, поэтому путь нового клиента от регистрации до первой покупки должен быть завершён и проверен. Жёсткого календарного дедлайна сейчас нет; ориентир разработки не позволяет исключать обязательные домены.

Не включай в v1: собственных курьеров и courier app, другие города, multi-kitchen, marketplace, JANTOK Market/Clean/Services, dark mode, основные подписки на неделю или один день, fitness-трекер и историю изменения веса, WhatsApp-интеграцию, email-авторизацию, Google Login, обязательный Apple Login, наличные, рассрочку, еженедельные платежи, premium-замены блюд, чат с курьером, фото подтверждения доставки, QR на упаковках. Kaspi, Apple Pay и Google Pay оставь на будущее; не подменяй ими обязательную оплату банковской картой.

## 6. Общие инварианты времени, денег и конфигурации

Для бизнес-календаря Астаны используй IANA timezone `Asia/Almaty`; время сервера храни как UTC instants, локальные даты обслуживания — отдельно как даты. Это технический выбор реализации. Время устройства пользователя не должно обходить cut-off. Сервер возвращает своё время, timezone и вычисленные дедлайны; mobile/admin показывают их согласованно.

Раздели `service_date`, дату платежа, время события, фактическую доставку, плановое окончание цикла и число оставшихся оплаченных дней. Не реализуй подписку через одно поле `expires_at = created_at + 30 days`.

Деньги храни целыми значениями в минимальной денежной единице с явно указанной валютой KZT; не используй floating point для платежей. Количество ингредиентов и себестоимость рассчитывай через Decimal и определённые единицы измерения. Прими единую политику округления и проверяй, что сумма распределённых частей равна исходной сумме.

Расчёт цены делай на backend через quote: состав, скидки, бонусы, доплаты, сумма к оплате, currency, версия правил и срок действия. Перед подтверждением оплаты перепроверяй quote. Изменение анкеты, участников, адреса, выбранного дня или конфигурации не должно оставлять незаметно устаревшую стоимость.

Храни версии применённых pricing, nutrition, refund и loyalty rules. Зафиксированная покупка и оплаченный цикл используют сохранённые условия; изменение настроек не переписывает старые платежи, чеки, рецепты заказов и расчёты возврата. Для будущих циклов используй новые правила с понятным клиенту расчётом.

Все параметры из ТЗ должны иметь типы, валидацию, permissions, аудит, эффективную дату/версию там, где это влияет на действующие обязательства, и обновление кэша. Нельзя реализовать настройки как беспорядочный JSON, который позволяет сохранить несовместимые значения без проверки.

Настраиваемость не отменяет продуктовые границы v1: например, изменение конфигурации не должно незаметно включить отдельные недельные тарифы, платные delivery slots или другие города. Для таких изменений требуется новое прямое решение владельца.

## 7. Авторизация, сессии и владельцы системы

Реализуй регистрацию и вход по номеру телефона и SMS OTP. Email и пароль клиента не нужны. Для аккаунта обязательны имя и фамилия; дата рождения, пол и другие параметры заполняются в анкете питающегося человека.

Реализуй отправку OTP, повторную отправку с интервалом, expiration, одноразовое использование, ограничение числа попыток, rate limits по номеру/IP/устройству, защиту от перебора и безопасные ответы. Не возвращай OTP в обычном API-ответе и не пиши его в production-логи. Нормализуй номера в согласованный международный формат.

Поддержи access/refresh sessions, ротацию refresh token с обработкой повторного использования, logout текущего устройства и отзыв сессий. Один аккаунт должен одновременно работать на нескольких устройствах: вход второго взрослого не должен автоматически выбрасывать первого. Device push tokens связывай с конкретными сессиями/устройствами.

OTP provider подключай через интерфейс. В local можно использовать dev inbox или terminal sink и отдельные тестовые номера. Такой режим должен быть технически запрещён в production. Никаких постоянных универсальных OTP или скрытого admin bypass.

Для сотрудников реализуй защищённый вход и назначение прав на backend. Наличие frontend route `/admin` само по себе не даёт доступ. Создай механизм безопасного первоначального назначения **двух Super Admin**: технического основателя и второго участника, отвечающего за бизнес/маркетинг. Их реальные номера и доступы поступают из конфигурации/инициализации, а не придумываются и не публикуются в seed для production. Локально используй отдельные демонстрационные учётные записи.

## 8. Household и анкета каждого человека

В v1 один основной клиентский аккаунт владеет одним household. В household может быть один, два, четыре и больше участников; не ограничивай семью четырьмя людьми из-за макета. Для каждого участника создай отдельный профиль питания и связи с его ограничениями.

Onboarding называй «Анкета». Сначала спроси состав семьи, затем заполни анкеты всех питающихся, адрес и необходимые параметры доставки, после этого покажи рекомендации и окончательную цену. Сохраняй прогресс анкеты и возвращай пользователя к незавершённому шагу после перезапуска.

Поля анкеты:

- Имя/идентификатор участника; дата рождения и вычисляемый возраст.
- Пол, рост, вес.
- Уровень активности, спорт и характер тренировок.
- Цель: похудение, поддержание, набор веса, спорт.
- Тип питания, предпочтения, нежелательные продукты.
- Аллергии: справочник плюс свободный текст для редких случаев; явное «нет известных аллергий» вместо молчаливого пропуска обязательного шага.
- Размер порции: ручной выбор или принятие рекомендации.

Возрастные группы: 0–5, 6–12, 13–17, 18+. У первых трёх групп могут отличаться нормы и цены. Для 13–17 категория питания/цены определяется правилами системы. Категорию для уже оплаченного периода фиксируй; не меняй стоимость посреди цикла незаметно из-за дня рождения.

Изменение профиля должно пересчитать подходящие будущие рекомендации и проверить запланированные блюда. История исполненных заказов сохраняется. Новая аллергия, затрагивающая уже зафиксированный заказ, должна создать явный конфликт и задачу ответственному сотруднику; нельзя молча оставить опасный заказ или тихо переписать уже выданный production list.

## 9. Nutrition Engine и безопасность выбора блюд

Создай детерминированный, тестируемый Nutrition Engine. Вход: возраст, пол, рост, вес, активность, спорт, цель, diet type, allergies, dislikes, preferences, portion preference. Выход: рекомендуемая калорийность, белки/жиры/углеводы, размер порции, разрешённые и заблокированные блюда, предпочтения и предложение меню на 30 дней обслуживания.

Формулы, коэффициенты, диапазоны и ограничения централизуй в versioned nutrition rules. У каждого набора правил должны быть область применимости и статус согласования. Не выдавай выдуманные детские медицинские нормы за утверждённые правила JANTOK. Для детских возрастов используй отдельно настраиваемые и согласуемые правила; если подходящего production-набора нет, предусмотрены понятная причина и ручная проверка специалистом. В local подготовь явно демонстрационные сценарии, чтобы интерфейс и весь процесс можно было проверить.

Нутриционные рекомендации не должны представляться диагнозом или лечебным назначением. Пользователь и уполномоченный администратор могут корректировать рацион и порцию в пределах разрешённых правил. Большая порция не означает автоматическую доплату: это отдельное правило pricing/nutrition configuration.

Поддержи расширяемый справочник типов питания: обычное, vegetarian, halal, без рыбы, без молочного и другие. Все варианты должны соответствовать общему halal-ограничению. Валидацию выполняй по реальному составу, рецепту и атрибутам ингредиентов.

Аллергены проверяй **для конкретного member**, включая исходное блюдо, модификации, добавленные ингредиенты, add-ons и питание гостя. При конфликте покажи красное предупреждение и заблокируй подтверждение на backend для этого человека. Другому члену семьи такое блюдо может быть доступно. Отзыв, скидка или администраторская кнопка не отменяют проверку аллергенов.

Свободный текст аллергии нельзя просто игнорировать: неизвестное ограничение помечай как требующее классификации/проверки. Удаление ингредиента не должно автоматически означать отсутствие следов аллергена или производственного риска: учитывай явно разрешённую рецептурную модификацию и metadata кухни. Непроверенный состав не выдавай за безопасный.

Учитывай историю выбора и оценок для ранжирования подходящих вариантов, не нарушая жёсткие ограничения. Если подходящего блюда нет, верни объяснимую проблему и задачу админу; не подставляй запрещённое блюдо ради заполненного календаря.

## 10. Меню и карточки блюд

Создавай план на 30 дней обслуживания. Клиенту показывай меню на 7 календарных дней вперёд с отметками пауз/пропусков; это рабочее уточнение отображения недельного календаря. По мере сдвига подписки продлевай план, чтобы оплаченные дни оставались обеспечены меню.

Каждый активный member получает завтрак, обед и ужин. Для каждого meal slot есть рекомендованное блюдо и заранее подготовленные допустимые альтернативы. Замена бесплатная до cut-off; premium-замен нет. Нельзя назначить блюдо, отсутствующее в опубликованном меню нужной даты/слота.

В карточке блюда показывай фото, название, kcal, белки, жиры, углеводы, вес, состав, аллергены, рейтинг и отзывы. Переводы названия/описания/состава должны поддерживать kk/ru/en через локализованные данные, а не через одно поле только на русском.

Модификации:

- Удаление ингредиента разрешено только при наличии флага customization availability у рецепта/ингредиента.
- Добавление ингредиента разрешено только из допустимого списка, с ценой, остатком и проверкой ограничений участника.
- Пересчитывай итоговые состав, граммовку, БЖУ, аллергены и стоимость с учётом модификаций, используя реальные recipe quantities.
- Отличай дополнительный ингредиент в блюде от самостоятельного товара add-on. Рабочее допущение: ингредиенты подчиняются cut-off изменения меню, самостоятельные add-ons — собственному cut-off.
- Сохраняй snapshot рецепта, порции, состава и модификаций в заказе; последующее редактирование карточки не меняет старую упаковку и себестоимость задним числом.

## 11. Cut-off и финализация следующего дня

Реализуй серверный CutoffService, единый для mobile, admin, API, jobs, платежных подтверждений и всех редактирований заказа. Рабочие значения из ТЗ храни в settings:

| Операция на завтрашний день | Начальный рабочий ориентир |
| --- | --- |
| Изменение блюда/модификаций | До 13:00 текущего дня |
| Оплата и начало подписки завтра | До 13:00 текущего дня |
| Пропуск дня | До 14:00 текущего дня |
| Изменение адреса | До 14:00 текущего дня |
| Изменение delivery slot | До 14:00 текущего дня |
| Покупка самостоятельных add-ons | До 15:00 текущего дня |
| Финальная фиксация кухни | После последнего cut-off, исходный ориентир 15:05 |

«До» трактуй как строго раньше дедлайна; на самой границе изменение закрыто. Это техническое уточнение проверь граничными тестами. Не проверяй права на изменение только по статусу `SCHEDULED`: разные действия закрываются в разное время.

Время изменения настроек не должно ретроактивно отменять принятые и оплаченные обязательства. У каждой даты должен быть понятный набор применённых дедлайнов. Валидируй, что финализация кухни не происходит раньше последнего разрешённого изменения.

Для оплаты старта завтра ориентируйся на авторитетный статус и время успешной оплаты у провайдера, учитывая задержку webhook, а не на нажатие кнопки клиентом. Не обещай завтрашнюю доставку по неоплаченному checkout. При действительно позднем подтверждении применяй явную политику переноса/исключения и уведомление, не создавая заказ задним числом после production lock.

После дедлайна обычный клиент получает понятное объяснение и ближайшую доступную дату. Уполномоченный админ может внести исключение с причиной, аудитом, пересчётом production/packing/stock и уведомлением ответственных; такая операция не должна обходить аллергенные и финансовые инварианты.

## 12. Подписка, календарь, паузы, пропуски, участники и гости

Основной цикл содержит **30 оплаченных service days**, а не 30 календарных дней. Длительность хранится в настройках, начальное подтверждённое значение — 30. Старт в тот же день запрещён. Завтра доступно при своевременной успешной оплате; после cut-off первая возможная дата — минимум послезавтра. Пользователь также может выбрать более позднюю дату.

Создай явную модель service-day allocation/ledger: планирование, резервирование при фиксации заказа, использование, перенос, отмена и компенсация. Пропуск/пауза не должны одновременно списать и перенести один и тот же день. Рабочее допущение: окончательное использование оплаченного дня фиксируется после `DELIVERED`; проблемная доставка сохраняет резерв до решения, после которого проводится либо использование, либо возврат дня/компенсация. Не выдавай новые бесплатные дни бесконечно из-за зависшего статуса. Обработку неудачной доставки сделай явным административным процессом.

Пауза разрешена суммарно до 30 календарных дней в одном цикле, несколькими периодами. Предел конфигурируется. Даты не должны пересекаться некорректно или затрагивать уже исполненные дни. Для начала паузы применяй соответствующий дедлайн изменения ближайшего дня; зафиксированные заказы требуют разрешённого исключения.

Skip разрешён до своего cut-off. Пропущенный день не сгорает: перенеси его в конец цикла. Как рабочее допущение, отдельные skip не уменьшают лимит именно паузы; сохрани различие операций, отрази его в документации и сделай бизнес-политику явной. Повторный skip того же дня не добавляет ещё один день.

После pause/skip пересчитывай календарное окончание, будущие заказы, recurring add-ons, прогноз производства и jobs автопродления/уведомления. Бесплатный день от администратора храни отдельно от оплаченной стоимости: он не должен увеличить сумму денежного возврата.

Добавление постоянного участника:

1. Создать member и заполнить его анкету.
2. Определить реальные оставшиеся даты обслуживания, в которые он может включиться с учётом cut-off.
3. Рассчитать доплату через Pricing Engine: ориентир `monthly_member_price / 30 × eligible_remaining_service_days` с корректным распределением округления.
4. Подключить человека только после успешной оплаты/расчёта бонусами.
5. Синхронизировать конец участия с текущим циклом household; не создать ему отдельную произвольную месячную подписку.

Гость — временное питание на один или несколько выбранных дней в рамках активной подписки. Собери необходимые параметры питания и аллергии, рассчитай отдельную оплату, добавь порции в тот же Daily Order и доставку. Гость не меняет постоянный месячный состав семьи и не создаёт отдельный основной однодневный тариф.

Сделай просмотр статуса, оставшихся дней, календаря, пауз, пропусков, истории изменений, ручного продления и настройки автопродления. Исключи дублирование активных циклов/заказов при повторных запросах и параллельных действиях с разных устройств.

## 13. Pricing Engine и стоимость

Рассчитывай стоимость из состава household, возрастных категорий и актуальных правил. Поддержи стоимость взрослого/ребёнка по группам, применимые коэффициенты/скидки семьи, платные ингредиенты, add-ons, гостей, prorate, промокоды и оплату бонусами. Не добавляй неутверждённую доплату за большую порцию или район доставки.

Базовая структура расчёта: сумма стоимости участников + разрешённые дополнительные позиции − скидки − оплачиваемая бонусами часть = денежная сумма к оплате. Для всех сумм возвращай детализацию и объяснение применённых правил.

Числа около 350 000 ₸ за подписку и около 200 000 ₸ за одного человека в ТЗ — обсуждавшиеся примеры, **не окончательные цены**. В local можно использовать явно обозначенные demo pricing rules. Для production должна требоваться активированная бизнесом конфигурация; не публикуй выдуманные цены как согласованные.

Сохраняй неизменяемую финансовую детализацию покупки по участникам, service days и отдельным позициям. Это должно позволять точно вычислить prorate, стоимость неиспользованного питания, частичный возврат и влияние скидок/бонусов. Не пересчитывай старый возврат по сегодняшнему каталогу цен.

Раздели состояние финансовой покупки, состояние банковской операции и состояние подписки/заказа. `Payment succeeded` не равно `Order delivered`. Бесплатная операция или полностью бонусная покупка должны корректно завершаться без банковского списания на нулевую сумму.

## 14. Платежи, сохранённые карты и чеки

На старте реализуй банковскую карту, оплату всего месячного цикла сразу, сохранённые способы оплаты через токенизацию провайдера, историю платежей, возвраты, чеки и автосписание. Данные PAN/CVV не должны попадать в базу, собственные формы хранения, аналитику или логи JANTOK. Используй защищённый checkout/SDK провайдера и храни только допустимые identifiers/tokens и маскированные metadata.

Поставщик платежей и поставщик фискализации в ТЗ **не выбраны**. Создай `PaymentProvider` и `FiscalizationProvider`, полноценные локальные симуляторы и контрактные тесты. Если в окружении уже указан реальный поставщик, реализуй адаптер по его официальной документации. Если его нет, не делай вид, что достаточно универсального HTTP URL и выдуманного JSON. Запиши конкретную внешнюю зависимость; весь остальной payment domain должен быть готов.

Платёжный процесс должен включать создание intent/checkout, сохранение pending operation, подтверждение от сервера провайдера, обработку ошибок/отмены/timeout, reconciliation зависших операций, привязку к покупке и безопасный повтор. Возврат пользователя по deep link сам по себе не подтверждает оплату. Подписка активируется только после авторитетного подтверждения либо завершённого внутреннего расчёта бонусами.

Для webhook проверяй подлинность доступным и документированным способом конкретного провайдера; сохраняй event ID и результат обработки. Повторы и события не по порядку не должны повторно активировать подписку, начислять бонусы, формировать refund или создавать чек. Сохраняй пригодные для диагностики обезличенные сведения, а не секреты или карточные данные.

Реализуй idempotency keys, уникальные provider operation IDs, транзакционность внутренних переходов и outbox/reconciliation для внешних вызовов. После network timeout сначала выясняй результат операции у провайдера; нельзя безусловно создать второе списание с новым ID.

Чек должен иметь отдельный жизненный цикл: ожидается, формируется, сформирован, ошибка, возвратный документ при необходимости. Квитанцию симулятора явно маркируй тестовой и не называй фискальным чеком. Поскольку фискализация остаётся обязанностью бизнеса/админа, реализуй раздел контроля, прикрепление/регистрацию реального документа с проверяемыми metadata и статусом, а также интерфейс автоматического адаптера. Ошибка отправки чека не должна создавать повторный платёж.

## 15. Автопродление

Поддержи явное согласие на автопродление, сохранённый token/payment mandate провайдера, просмотр следующих условий, возможность отключить функцию и предварительное уведомление за 3–5 дней. Точное окно хранится в settings; начальный demo-вариант можно выбрать внутри этого диапазона и обозначить как настройку.

Продление связано с окончанием оплаченных service days, а не с фиксированным числом месяца. Pause, skip и добавленные дни должны менять ожидаемую дату продления и связанные jobs без двойных списаний.

Перед списанием проверь действующий мандат, отсутствие отмены, актуальность уведомления и цену следующего цикла. Рабочее допущение: если дата/стоимость изменились так, что требуемое предварительное уведомление больше не соблюдено, перенеси автоматическое списание или запроси ручное подтверждение; не списывай неожиданно.

Оплаченный следующий цикл запланируй после текущего. Не допускай пересекающихся дублирующих заказов. При payment failure не считай продление успешным, покажи понятную проблему и действие повторной оплаты. Retry-политику ограничь и настрой; бесконечные попытки запрещены.

## 16. Возвраты, отмены и компенсации

Реализуй исходные бизнес-правила:

| Ситуация | Требуемое поведение |
| --- | --- |
| До первой доставки | 100% возврат суммы соответствующей покупки с корректным восстановлением бонусной части |
| В первые 7 дней | Возврат за неиспользованную часть подписки |
| После 7 дней | Обычный добровольный возврат недоступен |
| Ошибка JANTOK, недоставка, качество | Отдельный административный процесс компенсации/возврата независимо от стандартного окна |

В ТЗ не зафиксировано, как считать границу первых 7 дней. Рабочее допущение: окно начинается с первой подтверждённой доставки и длится 7 календарных дней в бизнес-timezone; точную границу опиши, конфигурируй и покрой тестами. Не называй это уже юридически утверждённой политикой.

Упоминание возможного сгорания последних 5–6 дней не вводит второе противоречащее правило. Базово действует запрет обычного возврата после первых 7 дней; раннее прекращение доставки, оставшиеся права на питание и компенсации должны иметь явные состояния и понятное подтверждение пользователя. Не удаляй остаток без записи о причине и применённой политике.

Возвращай банковскую часть через провайдера в пределах реально удержанной и ещё не возвращённой суммы; бонусную — обратной ledger-операцией. Денежная компенсация сверх исходной оплаты, если бизнес захочет её выдавать, не должна маскироваться под refund существующего платежа. Учитывай скидки, уже использованные дни, доплаты участников, add-ons и возвраты отдельных позиций.

Проверь случаи частичного refund, повторного запроса, нескольких refund для одного платежа, pending/refund failure и повторного webhook. Лимиты сумм и прав проверяй на backend в транзакции. Причина, actor и результаты внешней операции должны сохраняться.

Начисленные за отменённую покупку welcome/referral/CLUB-преимущества корректируй обратными операциями, а не удалением истории. Если бонусы уже потрачены, сохраняй отдельное обязательство/корректировку и ограничивай дальнейшее расходование по явной политике; не списывай деньги с карты без согласия и не теряй следы расхождения.

Создай настраиваемые тексты условий, consent version и launch-задачу согласовать оферту, возвраты и фискализацию с бизнесом для Казахстана. Не утверждай соответствие законодательству на основании одного этого промпта.

## 17. Дополнительные товары и постоянные add-ons

Каталог должен поддерживать напитки, десерты, салаты, snacks, кофе, воду, фрукты и новые категории, создаваемые администратором. У товара есть локализация, фото, описание/состав, ограничения/аллергены, цена, доступность, единица, остаток и количество.

Разреши разовую покупку на конкретную дату и recurring add-on на дни подписки. Количество x1, x2, x3 и далее; постоянная покупка может иметь отдельную более низкую цену. Покупка оплачивается деньгами, бонусами или их комбинацией. Add-on включается в существующую утреннюю доставку без доплаты за район.

Не отправляй add-ons в неоплаченные, приостановленные или пропущенные дни по ошибке. Для постоянных позиций сохраняй количество оплаченных/оставшихся единиц и привязку к service days. При переносе дня переноси и соответствующую оплаченную единицу; отмены и частичные возвраты проводи явно. Не списывай их стоимость повторно при регенерации календаря.

До оплаты проверь add-on cut-off, наличие действующей подписки, доступность дня и остаток. Если товар предназначен конкретному человеку, свяжи его с member для персональных проверок; если он общий, показывай состав и риски семье, не притворяясь, что у него автоматически есть подходящий получатель.

## 18. Промокоды, бонусы, referral и JANTOK CLUB

### Промокоды

Поддержи процентную скидку, фиксированную скидку KZT и начисление бонусов, с расширяемой моделью будущих механик. Ограничения: начало/окончание действия, общий лимит, лимит на пользователя, только первая подписка, минимальная сумма, применимые товары/операции и правила совместимости.

Определи и зафиксируй порядок применения: применимые скидки, затем бонусная оплата, затем банковский остаток. Рабочее допущение — один промокод на покупку, пока в настройках не утверждена совместимость нескольких; не придумывай скрытое суммирование скидок. Не допускай отрицательной стоимости. Резерв использования и его подтверждение должны переживать конкурирующие checkout и отмену оплаты.

### Бонусный ledger

Подтверждённые правила: welcome bonus 10% от первой успешной оплаты, 1 бонус = 1 ₸, бонусы бессрочные, разрешена оплата до 100% суммы при достаточном доступном балансе. Использование — подписка, add-ons и другие разрешённые покупки.

Рабочее уточнение базы welcome: фактически полученная денежная часть первой успешно оплаченной подписки после скидок, без повторного начисления на потраченные бонусы; полностью бонусная покупка не создаёт искусственную денежную базу. Сохрани это как явную настраиваемую политику, поскольку точная база в master specification не расписана.

Реализуй wallet и неизменяемые транзакции: начисление, резерв, списание, снятие резерва, возврат, компенсация/сторно. Баланс может кэшироваться, но должен воспроизводиться по ledger. Двойной запрос, два устройства или два платежа не могут потратить одни бонусы дважды. Откат делай компенсирующей записью со ссылкой на исходную операцию.

### Referral

Создай персональный referral code/link и путь применения в регистрации/первой покупке. Награда начисляется после реальной успешной оплаты подписки приглашённым, а не после регистрации. Храни attribution, событие квалификации, расчёт награды и начисление.

Размер награды растёт по количеству успешно приглашённых платящих друзей. Все уровни и база процента настраиваются. Примеры «1 друг ≈ 2%, 3 ≈ 5%, 5 ≈ 10%» не утверждены и не должны стать production-дефолтом.

Как рабочий вариант начисляй награду за новое квалифицирующее событие по достигнутому tier без пересчёта всех старых наград задним числом; правило должно быть видно в настройках и документации. Исключи self-referral, повторную квалификацию одного приглашённого и дубли webhook. Корректируй последствия возврата исходной покупки через ledger.

Фраза про оплату 12-го месяца бонусами означает самостоятельное накопление достаточного баланса. Автоматически бесплатного 12-го месяца после 11 оплат нет.

### JANTOK CLUB

Членство открывается после настраиваемого количества оплаченных циклов. Уровни, названия, пороги, бонусные коэффициенты и преимущества управляются в Admin Panel. Member/Silver/Gold/Platinum и пороги 3/6/12/24 — примеры, а не утверждённая сетка.

Как техническое уточнение считай месяцы через квалифицирующие оплаченные циклы по 30 service days, не через календарные месяцы существования аккаунта. Отдельно опиши, как влияют полный и частичный возврат; не повышай уровень за неоплаченное создание подписки, гостя или бесплатный день.

Экран CLUB: баланс, доступные/зарезервированные бонусы, текущий уровень, история операций, приглашённые друзья, прогресс до следующего уровня/награды и преимущества. Применение преимуществ проверяется сервером. Историю друзей показывай без лишнего раскрытия их персональных данных.

## 19. Адреса, зона и слоты доставки

Разреши максимум 5 сохранённых адресов. Лимит хранится в settings, начальное значение — 5. Есть основной адрес и пользовательские названия: «Дом», «Работа» и другие. Собери улицу/дом, подъезд, этаж, квартиру/офис, домофон, ориентиры и координаты, достаточные для доставки до двери.

Реализуй проверку зоны доставки на backend по настраиваемой подтверждённой геометрии зоны Астаны/геоданным, а не по наличию слова «Астана» в строке и не по огромному прямоугольнику, включающему посёлки. Для local допускается явно demo zone; production требует реально согласованной зоны. Ручной ввод адреса должен работать без предоставления геолокации телефона.

Основной адрес можно изменить, на конкретную дату можно выбрать другой. Сохраняй address snapshot в заказе/доставке; удаление или изменение записи address не переписывает историю и уже отправленный заказ курьеру.

Доставка включена в цену подписки и не зависит от района внутри зоны. Три бесплатных слота: **06:00–08:00, 07:00–09:00, 08:00–10:00**. Перекрытие слотов принято осознанно. На старте нет лимита количества заказов на слот. Не добавляй скрытую slot fee, автоматическую нормализацию или capacity cap без решения бизнеса.

Слоты и зона настраиваются. Не удаляй слот, используемый уже зафиксированным заказом, без управляемой миграции. Если провайдер не может обеспечить такой интервал, покажи проблему оператору и зафиксируй ограничение интеграции; не обещай клиенту гарантированный SLA, который сервис не предоставляет.

## 20. Яндекс Доставка и клиентское отслеживание

Используй стороннюю Яндекс Доставку. Собственного courier app, управления персоналом курьеров и собственного оптимизатора маршрутов в v1 нет. Один household получает одну конкретную доставку на день, содержащую комплекты всех участников, гостей и add-ons.

Создай `DeliveryProvider` с операциями:

- `calculateDelivery()`;
- `createDelivery()`;
- `cancelDelivery()`;
- `getStatus()`;
- `getCourier()`;
- `getTracking()`;
- `getETA()`.

Yandex-адаптер должен использовать реальные методы выбранного API, account/contract и статусы. Перед реализацией изучи [официальный список методов Яндекс Доставки](https://yandex.ru/support/delivery-profile/en/api/express/overview) и [порядок получения API-доступа](https://yandex.ru/support/delivery-profile/en/api/express/quickstart). Наличие метода в общей документации не является подтверждением его доступности по договору JANTOK в Казахстане: это проверь отдельно и явно отрази в интеграционной конфигурации.

Backend автоматически инициирует доставку для готового заказа с учётом выбранного утреннего окна и реальной схемы вызова/подтверждения провайдера. Не вызывай курьера сразу ночью только потому, что статус перешёл в `READY`; readiness и запланированное время dispatch — разные условия. Не заставляй сотрудника вручную создавать каждую обычную доставку.

Реализуй idempotency, повторы с backoff, ограничение retries, reconciliation после timeout, сохранение provider ID и событий. У daily order может быть только одна активная доставка. Повторные попытки после отмены/сбоя сохраняй отдельно; они не должны стирать историю или создавать одновременно двух курьеров.

Используй webhook, если такой механизм действительно доступен выбранной интеграции; иначе корректный polling с лимитами. Не придумывай endpoint webhook, событие или возможность подписи, которых у провайдера нет. Сделай явное отображение external statuses во внутреннюю модель, обработку неизвестных/запоздавших событий и защиту от регресса финального состояния.

В приложении клиента нужны карта/отслеживание, статус, ETA и звонок курьеру. Координаты, контакт, tracking URL и ETA получай через поддерживаемые возможности провайдера. Если конкретное поле временно недоступно, показывай честное состояние и доступный fallback, например tracking link или связь с поддержкой. Не генерируй правдоподобный ETA или движущуюся точку в production.

Номер курьера может быть маскированным/временным; получай его заново после переназначения. Звонок запускает системный dialer. Чат с курьером не создавай. Отдельный комментарий курьеру в заказе не обязателен: нужные детали находятся в адресе. Отдельной механики бесконтактной доставки и фото подтверждения нет.

Поддержи `NO_ANSWER` и `DELIVERY_FAILED` с понятным действием для поддержки. Недоставка не должна автоматически считаться доставленным питанием. Решение о повторной доставке, возврате или компенсационном дне принимает уполномоченный сотрудник через явную операцию.

## 21. Daily Order и согласованные переходы статусов

Daily Order создаётся для household на дату обслуживания. Внутри: участники, три meal slots каждого, их модификации, временные гости и дополнительные товары. Одна семья не должна получить отдельные courier orders на каждого участника.

Реализуй последовательность статусов из ТЗ:

`SCHEDULED → LOCKED → IN_PRODUCTION → COOKED → PACKING → READY → DELIVERY_CREATED → COURIER_ASSIGNED → COURIER_PICKED_UP → ON_THE_WAY → ARRIVED → DELIVERED`.

Дополнительные состояния: `SKIPPED`, `CANCELLED`, `DELIVERY_FAILED`, `NO_ANSWER`, `REFUNDED`. Учитывай, что финансовый refund может происходить после физической доставки: сохраняй отдельное финансовое состояние и историю исполнения, а не стирай факт `DELIVERED` одним полем. Если API выдаёт общий `REFUNDED`, сохраняй underlying fulfillment status.

Создай таблицу допустимых переходов: кто/что инициирует, условия, побочные эффекты, audit/event, возможность retry. Не разрешай случайный `PATCH status` любым значением. Ручные исключения оформляй командами с permissions и причиной.

Daily order generator и finalization jobs должны быть идемпотентными, переживать рестарт и корректно обрабатывать паузы, пропуски, продление, новых members/guests и оплаченность. Редактирование с двух устройств должно использовать version/optimistic concurrency; stale update не перетирает более новую оплату или изменение.

## 22. Кухня, production list, packing list и этикетки

Реализуй полноценный операционный цикл одной кухни. Production list агрегирует потребность по блюдам, порциям и ингредиентам, а не заставляет повара читать отдельные клиентские заказы.

Каждое блюдо имеет recipe quantities и единицы измерения на порцию, версию рецепта, факторы выхода/потерь при необходимости, разрешённые модификации. Для даты рассчитывай количество порций и общую потребность ингредиентов. Например, количество курицы в рецепте умножается на число соответствующих порций и переводится в складскую единицу.

Агрегируй отдельно несовместимые варианты: другое количество/размер порции, исключённый ингредиент, платная добавка, аллергенное ограничение. Не объединяй обычный омлет и его реально допустимую модификацию в одну неразличимую строку. Учитывай взрослых, детей, гостей и add-ons.

Предварительный forecast и финальный production list — разные состояния. После cut-off кухня получает зафиксированную версию. При разрешённом административном изменении создай новую ревизию/дельту, покажи её сотруднику, пересчитай складские резервы и packing tasks. Нельзя незаметно поменять уже распечатанный документ.

Покажи план, фактический выпуск, недовыпуск/перевыпуск, ошибки, статусы «готовится/готово». Запись факта производства и соответствующие stock movements должны выполняться согласованно и не повторяться при двойном клике.

Packing tasks группируются по household/заказу и member. Упаковщик видит точный состав коробок, индивидуальные изменения и add-ons, отмечает каждую позицию, затем завершает комплектацию. Неполную упаковку нельзя автоматически объявить готовой к курьеру.

Печать этикеток обязательна. Укажи бренд, имя/идентификатор клиента/участника, дату, состав комплекта и номер заказа. Добавь необходимую маркировку индивидуальных ограничений и данные конкретной позиции там, где это предотвращает путаницу. Не печатай лишние данные анкеты. QR в v1 не нужен.

Принтер ещё не выбран. Создай пригодные для печати PDF/HTML layouts с настраиваемым размером этикетки, preview, повторной печатью и историей. Не объявляй проверенной совместимость с неизвестной моделью принтера. Production list и packing list тоже должны иметь удобные печатные/экспортируемые версии.

## 23. Склад, поставщики, закупки, списания и себестоимость

Inventory входит в v1 целиком как прикладной рабочий домен, а не обещание «добавим потом». Реализуй:

- Ingredients с единицами измерения, аллергенами, категориями и ценовыми данными.
- Текущий фактический остаток, доступный остаток с учётом резервов, минимальные/критичные уровни.
- Неизменяемую историю движений.
- Suppliers, purchases и purchase items, приёмку закупок и закупочные цены.
- Waste entries: количество, причина, дата, ответственный/смена.
- Согласованные пересчёты и корректировки с причиной и аудитом.

Типы движений из ТЗ: `PURCHASE`, `PRODUCTION`, `WASTE`, `CORRECTION`, `RETURN`, `TRANSFER`. Поддержка TRANSFER не означает несколько кухонь; это может быть перемещение между местами хранения в единственном контуре. Не строй multi-kitchen архитектуру ради одного enum.

Нормализуй g/kg, ml/l и штуки с допустимыми преобразованиями. Не складывай граммы с миллилитрами без известного коэффициента конкретного ингредиента. Закупка создаёт приход после подтверждённой приёмки, прогноз не списывает фактический склад, а подтверждённое производство создаёт расход. Отдельно обрабатывай резерв и фактическое движение.

Рабочий выбор оценки запасов — взвешенная средняя стоимость при поступлении, с сохранённой стоимостью расхода и рецептурного snapshot. Если существующее окружение уже использует другую корректную модель, сохрани её и документируй. Считай стоимость блюда, дневного комплекта, оплаченного цикла, food cost, waste cost и gross margin воспроизводимо. Разделяй предварительную себестоимость и фактическую.

Складская корректировка/возврат не должны бесследно менять прошлое. Refund клиенту сам по себе не означает физический возврат пригодных ингредиентов на склад. Исключи двойное включение одного расхода в production и waste cost. Проверяй отрицательные остатки и конфликты конкурентного списания; исключение требует специального права и причины, если вообще разрешено политикой.

## 24. Отзывы, поддержка и коммуникации

### Отзывы о блюдах

Рейтинг — 1–5 звёзд и текстовый комментарий. Отдельные публичные ❤️/👎 не создавай. Отзывы публикуются сразу, видны другим клиентам; пользователь может удалить свой отзыв. Администратор может скрыть или удалить отзыв с правом, причиной и аудитом. Используй soft delete/историю модерации там, где это нужно для воспроизводимости действий.

Зафиксируй правило права на отзыв: рабочее допущение — клиент оценивает реально полученное блюдо с привязкой к своей позиции заказа; это защищает от произвольной накрутки. Не раскрывай публично телефон, возраст, аллергию или полный состав household автора. Средний рейтинг должен корректно учитывать удаление/скрытие, а алгоритм рекомендаций — историю оценок конкретного участника, если member указан.

### Встроенная поддержка

Реализуй постоянные support threads и messages, realtime, историю, статусы обращения, непрочитанные сообщения, ответ сотрудника из Admin Panel, вложения-фото и возможность позвонить в поддержку. Номер поддержки хранится в settings.

Обращение можно связать с конкретным Daily Order. Причины: не привезли, опоздали, повреждено, невкусно, не то блюдо, другое; комментарий свободный. Можно отправить положительную обратную связь через тот же механизм. Связь с заказом проверяется по ownership на backend.

Разрыв WebSocket не должен терять отправленные сообщения: сохраняй их в базе, применяй client message ID/dedup, reconnect и загрузку пропущенной истории. Авторизуй комнаты и каждое действие; клиент не может подписаться на чужой household/thread, изменив ID. Если realtime недоступен, история и отправка должны восстанавливаться через API.

Фото сохраняй в object storage с проверкой размера/формата и авторизованным доступом. Не помещай приватные жалобы в публичный bucket. Удаляй лишние metadata изображений там, где это возможно и нужно для приватности.

### Push и SMS

Основной канал сервисных и продуктовых уведомлений — push. SMS нужны для OTP и необходимых auth-сценариев. Email и WhatsApp не подключай.

События: заказ готовится, курьер выехал, актуальное приближение доставки/ETA, доступно меню на завтра, напоминание о cut-off, предварительное уведомление об автопродлении, результат оплаты/продления, важная проблема заказа/ответ поддержки.

Маркетинговые push разрешены только с соответствующими пользовательскими настройками/согласиями. Раздели сервисные и рекламные предпочтения, kk/ru/en templates, планирование и историю отправок. Храни notification records и результаты провайдера; не повторяй одно уведомление бесконечно после рестарта worker.

Push payload не должен раскрывать медицински чувствительные сведения на экране блокировки. Неверный device token отключай по результату FCM. Deep link должен открывать конкретный разрешённый пользователю экран после восстановления auth. Запрет notification permission не должен ломать приложение; важное состояние остаётся доступно внутри него.

Отдельно ограничь DB privileges приложения и мигратора; не утверждай абсолютную неизменяемость данных от владельца самой БД. Сохраняй историю soft-deleted объектов и изменения настроек. Защити систему от случайного удаления последнего действующего Super Admin.

Раздел настроек должен реально управлять backend-поведением и обновляться без релиза mobile. Обязательные группы:

- Длительность цикла в service days, максимальная пауза и связанные политики переноса.

- Auto-renew settings, consent и срок уведомления.
- Refund rules, границы окна и компенсационные политики.
- Supported languages, локализованные notification templates и контакты поддержки.
- Необходимые операционные параметры label printing, low-stock thresholds и повторов jobs.

Секреты провайдеров, private keys и signing credentials не должны редактироваться обычным текстом в общей таблице настроек. Конфигурация бизнес-правил и secret management — разные механизмы.

Подготовь экран/проверку production-конфигурации, чтобы demo-значения нельзя было незаметно принять за рабочие. Не добавляй пользователю приложения технические предупреждения на каждом шаге; такие сведения предназначены сотрудникам и launch-процессу.

## 29. Физическая модель данных и миграции

Перед основными доменами спроектируй физическую PostgreSQL/Prisma schema, enum, PK/FK, relations, constraints, indexes и стратегию soft delete. Реализуй миграции и отрази фактическую схему в ERD. Не оставляй проект на уровне списка сущностей.

Минимальные домены и данные из master specification:

| Домен | Сущности и связи, которые нужно отразить |
| --- | --- |
| AUTH | users, user_sessions, device_tokens, otp verification metadata |
| FAMILY | households, household_members, member_profiles, activities, goals, preferences, member_allergies |
| NUTRITION | nutrition_profiles, diet_types, nutrition_rules и их версии |
| MENU | meals, meal_translations, ingredients, allergens, meal_ingredients, ingredient_allergens, menus, menu_days, menu_options |
| SUBSCRIPTIONS | subscription config, price_rules, subscriptions, subscription_members, service days, pauses, changes и grants |
| ORDERS | daily_orders, order_members, order_meals, order_addons, snapshots и события |
| ADD-ONS | addons, translations, recurring_addons и оплаченные allocations |
| PAYMENTS | purchase/quote, payments, tokenized payment_methods, payment_events, refunds, receipts и денежные allocations |
| LOYALTY | bonus_wallets, bonus_transactions, holds, promo_codes/usages, referrals/rules/tiers, club_levels/memberships |
| DELIVERY | addresses, deliveries, delivery_events, provider metadata, attempts |
| KITCHEN | production_batches/items, revisions, packing_tasks/items, label metadata |
| INVENTORY | inventory_items, movements/reservations, suppliers, purchases/items, waste_entries |
| SUPPORT | support_threads/messages, attachments, reviews |
| SYSTEM | employees, roles, permissions, role assignments, audit_logs, notifications/templates, settings, analytics_events |
| RELIABILITY | idempotency records, webhook inbox, transactional outbox, job/reconciliation metadata там, где нужны для гарантий |

Ключевые связи:

- User 1:N Sessions/Devices; в v1 User владеет одним Household.
- Household 1:N Members и 1:N последовательных Subscriptions.
- Member имеет отдельный профиль и N:M ограничения/предпочтения/активности.
- Subscription N:M Members через subscription_members с датами/ценами участия.
- Subscription 1:N Service Days; каждый обслуживаемый household/date имеет не более одного действующего Daily Order.
- Daily Order 1:N Order Members; каждый участник имеет ровно необходимые три meal slots для полного дневного рациона.
- Meal N:M Ingredients через рецепт с amount/unit; Ingredient N:M Allergens.
- Daily Order имеет 0..1 активную Delivery и историю отдельных попыток; Delivery 1:N Events.
- Production items используют точный recipe/portion/customization snapshot.
- Ingredient/Inventory Item 1:N Stock Movements.
- Payment связан с конкретной покупкой/доплатой; Refund с Payment и allocations.
- User/Wallet 1:N Bonus Transactions, каждая корректировка ссылается на основание.
- Review связан с User, Meal и подтверждающим Order Item; member добавляется при персональной оценке.
- Audit Log содержит actor и ссылку на объект/операцию без удаления при soft delete объекта.

Добавь DB-уровень защиты: уникальные phones/владение/operation IDs где применимо, уникальный активный order на дату, уникальные meal slots, dedup webhook/outbox events, ограничения неотрицательных допустимых сумм, допустимых количеств и ссылок. Уникальности с soft delete проектируй осознанно. Частичные индексы и ограничения, которые не выражает выбранная версия Prisma, реализуй SQL-миграциями и задокументируй.

Добавь индексы под календарь, очередь кухни, deliveries, history, support messages, audits и отчёты. Используй транзакции/блокировки/optimistic concurrency для бонусного баланса, возвратов, складского расхода и конкурирующих изменений заказа. Redis-lock не заменяет постоянные ограничения БД.

Миграции должны воспроизводиться на пустой базе. Demo seed должен быть идемпотентным и запрещённым в production. Не используй destructive schema reset как обычный способ запуска или обновления.

Обеспечь catch-up пропущенных jobs без создания вчерашнего питания как сегодняшней новой покупки. Failed jobs должны быть видимы администратору и повторяться осознанно.

Для каждого важного экрана реализуй loading, empty, error, retry, offline/read-only где уместно, pending и success states. Сетевой сбой не должен выглядеть как отсутствие подписки или нулевой баланс. Изменения цены/денег/рациона при offline не подтверждай как выполненные; повторять их можно только с корректной серверной идемпотентностью.

После возвращения из платёжного checkout, перезапуска приложения или восстановления сети считывай реальное серверное состояние. Сохраняй завершённость анкеты и выбранную навигацию там, где это полезно. Все приватные данные очищай из локального контекста при logout/смене аккаунта.

## 32. Дизайн, бренд и локализация

Создай цельный светлый, чистый, современный интерфейс для семейного питания. Продукт среднего сегмента, поэтому ясность и удобство важнее искусственной «люксовости». Нужны аккуратная типографика, понятная иерархия, качественные карточки, ясные primary/secondary actions и сдержанные анимации состояния.

Используй текущий утверждённый логотип и палитру JANTOK, если ассеты доступны. Не переделывай знак в новый food-logo. В исходном DOCX нет изображения логотипа и точных HEX: не утверждай, что восстановил их из текста. Сначала проверь файлы проекта/вложения. Если материалов нет, временно используй текстовый JANTOK и нейтральную светлую theme с централизованными заменяемыми design tokens; отметь отсутствие ассетов в integration/launch status и продолжай функциональную разработку.

Вынеси colors, spacing, typography, radii, elevations, icons и reusable states/components. Не размазывай временные цвета по всем экранам. Не применяй dark mode. Для food photos используй предоставленные/разрешённые изображения с локально воспроизводимыми assets; сохрани сведения об источнике/лицензии. При отсутствии изображения покажи аккуратное fallback-состояние, а не битую картинку или фото, выдаваемое за реальное блюдо JANTOK.

Адаптируй mobile к небольшим и большим телефонам, SafeArea, клавиатуре, системному Back и увеличенному шрифту. Проверь длинные русские/казахские подписи. Тапы, focus, semantic labels, контраст и reduced-motion не должны теряться ради анимации.

Локализация обязательна для kk/ru/en: интерфейс mobile и пользовательские уведомления полностью, admin с общей поддержкой переводов и завершёнными основными текстами. Для Flutter используй ARB/штатный механизм локализации; для переводимого backend-контента — translations tables/эквивалентные структуры. Локализуй plurals, даты, деньги и ошибки. Включи явный fallback без отображения внутренних translation keys пользователю.

Выбор языка сохраняется, переключение работает без переустановки. Язык устройства может задавать начальный выбор, а kk остаётся основным языком бренда. Не смешивай три языка внутри одного сценария. Семантика числа дней и сумм должна оставаться одинаковой во всех переводах.

## 33. Android сначала, iOS без переписывания приложения

Подготовь проект так, чтобы папка Flutter открывалась в Android Studio, зависимости разрешались, а приложение запускалось на Android emulator и реальном устройстве. Проверь совместимость Flutter SDK, Android SDK, JDK, Gradle и plugins по [официальной инструкции Flutter для Android](https://docs.flutter.dev/platform-integration/android/setup), а не по случайным старым snippets.

Создай рабочие `dev`, `staging`, `production` configurations/flavors или эквивалентную ясную схему. Базовый URL, публичные конфигурационные идентификаторы и окружение передавай через централизованный config/`dart-define`; backend secrets в приложение не попадают. Dev build должен явно отличаться от production.

Обеспечь понятное подключение к local backend: Android emulator использует адрес хоста, например `10.0.2.2`, физический телефон — достижимый адрес компьютера/настроенный туннель; `localhost` телефона не является компьютером. Не зашивай личный LAN IP в исходники. Добавь Android Studio run configuration или точную воспроизводимую команду для выбранной схемы.

Настрой Internet permission для нужных вариантов сборки, notification permission по версии Android, deep links, безопасный запуск checkout, фото-вложения через системные механизмы и необходимые обоснованные разрешения. Dev HTTP допускай только в dev-конфигурации; production — HTTPS. Не отключай TLS-проверку для удобства разработки.

Сразу создай/сохрани `android/` и `ios/`, не привязывай domain/data к Android APIs. Выбирай пакеты с подтверждённой поддержкой iOS, а native-интеграции изолируй. Для iOS подготовь структуру, конфигурационные шаблоны, permission descriptions, universal/deep links и места подключения push/payment/maps. Не обещай, что любая интеграция заработает на iOS автоматически без native-настроек.

Реальная iOS-сборка требует macOS и Xcode; публикация связана с аккаунтом разработчика и signing. Это отражено в [официальном руководстве Flutter по iOS](https://docs.flutter.dev/deployment/ios). Если подходящее окружение доступно, выполни проверку сборки на симуляторе/без distribution signing в поддерживаемом режиме. Если нет — честно отметь её как непроведённую, сохрани совместимую архитектуру и точный checklist, не задерживая Android-разработку.

Для Android получи проверяемый APK, а при доступной конфигурации — release APK/AAB. Не выдавай debug-signed сборку за готовый production-релиз. Не создавай и не публикуй постоянные production signing keys без решения владельца. Запиши реальные пути к полученным файлам и использованные команды.

## 34. Локальный полный сценарий без внешних секретов

Сделай приложение проверяемым сразу после установки необходимых SDK/runtime. Docker Compose должен запускать PostgreSQL, Redis, object storage, backend/API, worker и admin в согласованной сети; допустима дополнительная dev-схема запуска приложений на хосте с инфраструктурой в Docker.

Создай рабочие scripts/Make targets для setup, start, stop, migrate, seed, verify, backup и restore. Setup должен проверять зависимости, создавать только отсутствующие local env из безопасных шаблонов, генерировать локальные случайные секреты, применять миграции и demo seed по явному local-флагу. Не перезаписывай уже заполненные `.env` и пользовательские данные. Обычный start не должен сбрасывать базу.

Для каждого внешнего сервиса предусмотрены явные режимы `local simulator`, `provider sandbox`, `production` с проверкой конфигурации. В local:

- SMS попадает в защищённый dev inbox/terminal sink, с настоящими server-side OTP expiration и attempts.
- Payment simulator проводит pending/success/failure/refund события через тот же application service и inbox/webhook boundary, что и реальные подтверждения.
- Delivery simulator воспроизводит статусы, доступность ETA/contact и проблемные исходы; в интерфейсе/окружении ясно, что доставка тестовая.
- Push sink сохраняет уведомления для просмотра, не требуя Firebase-аккаунта.
- Receipt simulator создаёт только явно тестовые документы.
- Object storage реально сохраняет вложения/изображения и переживает перезапуск контейнера.

Не размещай simulator управления платежами/OTP/доставкой в production routes. Backend в production должен отказываться стартовать или включать соответствующую функцию с опасной demo-конфигурацией; никакого тихого fallback на fake provider. При временной ошибке настоящего сервиса не переключайся на симулятор.

Создай seed, позволяющий проверить продукт, а не одну пустую учётную запись:

- Два local Super Admin и сотрудники с ограниченными ролями.
- Клиент без подписки и с незавершённой анкетой.
- Одиночный клиент и семья с взрослыми/детьми разных категорий.
- Участник с известной аллергией, безопасные альтернативы и запрещённый вариант.
- Блюда для трёх meal slots, разные порции, рецепты, разрешённые модификации, переводы и меню на полный цикл.
- Подписки/заказы в типичных состояниях, skip/pause, добавление member, guest, recurring add-ons.
- Payment/refund сценарии, bonus ledger, промокоды, квалифицированный referral и demo CLUB levels.
- Production/packing, stock movements, supplier/purchase/waste и проблемная доставка.
- Support thread с фото и отзывы.

Seed-значения и fixtures должны быть детерминированными или привязанными к управляемой бизнес-дате, чтобы сценарии не ломались на следующий день. Чувствительные демоданные вымышленные, цены/нормы помечены demo. Реальные пользователи и секреты не копируются в репозиторий.

## 35. Безопасность, наблюдаемость и эксплуатация

Реализуй в рамках продукта:

- Backend RBAC и ownership checks для REST, WebSocket, файлов и exports.
- Защиту OTP, sessions, cookies/tokens, CSRF при cookie-auth admin, разумный CORS и request limits.
- Ограничение доступа к анкетам и чувствительным полям; минимизацию данных в UI/логах.
- Проверку входных DTO, upload formats/sizes и контроль идентификаторов ресурсов.
- Защищённое хранение секретов окружения, исключение их из Git и client bundle.
- Корректную проверку webhook и сохранение безопасной истории integration events.
- Транзакционность бонусов, денежных allocations, возвратов и складских движений.
- Idempotency и восстановление scheduled jobs после рестарта.
- Soft delete и сохранение обязательной бизнес-истории без бесследного стирания операций.
- Rate limits для чувствительных endpoints, доступность API только по ожидаемым ролям.

Добавь structured logs с correlation ID, health/readiness endpoints, контроль подключения к PostgreSQL/Redis/storage, видимость failed jobs и интеграционных ошибок. Различай проблему внешнего сервиса и собственную ошибку; не скрывай exceptions через пустой catch.

Подготовь backups PostgreSQL и object storage, настраиваемую retention, restore scripts и проверку восстановления на отдельном local/test окружении. Контейнеры должны иметь persistent volumes и корректное graceful shutdown. Не уничтожай volume при обычной остановке.

Отдели LOCAL, STAGING, PRODUCTION: разные secrets, базы, buckets, provider modes и настройки. Не проводи тестовые платежи и destructive seed на production. Подготовь Dockerfiles, Compose для local/staging, Nginx config с WebSocket и TLS termination, пример production env и процедуру миграций/обновления/rollback приложения.

Бизнес-активы по ТЗ находятся у технического основателя: домен, сервер, store accounts, payment/SMS/maps accounts. Пока домен/VPS/GitHub Organization/store accounts не созданы, используй безопасные placeholders и конфигурационные шаблоны. Зафиксируй необходимые доступы и резервных администраторов без хранения паролей в документации.

Не покупай домен/сервер, не создавай платные договоры, не списывай реальные деньги, не отправляй реальные массовые сообщения, не вызывай курьера и не публикуй приложение/сайт без отдельной авторизации на соответствующее действие. Это не мешает подготовить и локально проверить весь код, deployment configuration и staging runbook.

## 36. Порядок выполнения без остановок между частями

Организуй работу внутренними этапами, но считай их частями одного поручения:

1. Исследуй окружение и существующий код; зафиксируй scope, допущения и критерии в traceability.
2. Спроектируй схему данных, статусы, invariants и API contracts; создай миграции и основу runtime.
3. Сделай сквозную auth → household → анкета → адрес → рекомендации вертикаль на настоящем backend.
4. Добавь каталог/рецепты/аллергены, меню и Pricing Engine.
5. Реализуй purchase/payment foundation, подписку и allocation оплаченных service days.
6. Добавь календарь, cut-off, смену блюд/модификаций, skip/pause, добавление member/guest и add-ons.
7. Доведи payment/refund/receipt/auto-renew процессы и проверку конкурентных операций.
8. Реализуй kitchen → inventory → packing → labels → delivery dispatch/tracking.
9. Закрой loyalty/referral/CLUB, отзывы, поддержку, уведомления и все административные операции.
10. Доведи аналитику/экспорт, настройки, RBAC, audit и эксплуатационные конфигурации.
11. Пройди сквозные сценарии, визуально проверь mobile/admin, исправь сбои, собери Android.
12. Сверь весь scope с реализацией и подготовь фактический итог с доступными artifacts/командами и только настоящими внешними блокерами.

Порядок можно адаптировать к зависимостям существующего кода. Не откладывай фундамент платежей до момента, когда весь subscription domain уже построен на фиктивном `isPaid = true`. Поддерживай собираемое состояние проекта между существенными изменениями.

Исходный ориентир 1–1,5 месяца/6 недель — планирование владельца, а не повод остановиться после «недели 1» и не гарантия срока. Не расширяй scope новыми идеями вместо завершения v1. Новые идеи записывай в отдельный backlog.

После каждого законченного блока обновляй `docs/IMPLEMENTATION_STATUS.md`: что реально работает, какие проверки выполнены, ошибки, недостающие интеграции и следующее конкретное действие. При сокращении контекста или перезапуске агента используй этот файл, contracts и traceability, чтобы продолжать работу без повторного проектирования.

Не проси меня давать команду «продолжай» после внутреннего этапа. Пока среда позволяет исполнять задачу, переходи к следующей работе сам. Реальные лимиты сессии, отсутствие инструментов и разрешения нельзя обходить: если они прервали выполнение, сохрани точную точку восстановления и не объявляй весь проект завершённым.

Кратко сообщай прогресс по результатам и оставшимся проблемам. Не выводи в чат сотни строк логов или повторный план вместо работы. Не скрывай упавший тест и не ослабляй требование ради зелёного отчёта.

## 41. Работа на пределе одной сессии/контекста

Объём этого задания заведомо больше, чем можно надёжно реализовать за один непрерывный запуск без потери качества: у среды исполнения есть предел контекста, времени и числа инструментов за сессию. Прими это как рабочее условие, а не как повод сокращать v1 или скрывать нехватку времени.

- Работай так, чтобы состояние проекта в любой момент было согласованным: после каждого законченного модуля обновляй `docs/IMPLEMENTATION_STATUS.md` и `docs/REQUIREMENTS_TRACEABILITY.md` фактическим статусом, а не в самом конце.
- Если ты приближаешься к пределу контекста/времени сессии, не пытайся «дожать» оставшееся ускоренно и не заявляй о завершении того, что не проверено. Останови работу на чистой границе (закоммиченный рабочий код, актуальная документация), явно зафиксируй в `docs/IMPLEMENTATION_STATUS.md` точку продолжения: что сделано, что проверено, что осталось, с каким шагом продолжать дальше.
- Пиши `IMPLEMENTATION_STATUS.md` так, чтобы следующая сессия (в том числе твоя собственная в новом запуске) могла продолжить без повторного изучения всего проекта с нуля — конкретные файлы, команды и незавершённые переходы, а не общие фразы.
- Не переупорядочивай и не пропускай обязательные домены ради того, чтобы формально «закрыть» финальный ответ раньше срока. Приоритет — реально работающий сквозной цикл (раздел 37), затем остальные домены по разделу 2.
- Если для полного v1 по факту требуется несколько последовательных запусков этого же промпта, это ожидаемо и не является нарушением задания «единым промптом»: единым остаётся объём требований и правила принятия решений, а не гарантия физического завершения за одно обращение к модели.
