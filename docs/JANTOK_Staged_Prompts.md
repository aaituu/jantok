# JANTOK — поэтапные промпты для Codex

## Как этим пользоваться

1. Сначала положи в проект файл `docs/JANTOK_MASTER_SPEC.md` — это твой обновлённый `JANTOK_Codex_Full_Development_Prompt.md` (с разделом 41 про границы сессии). Он остаётся единым источником правды по требованиям; поэтапные промпты ниже только управляют **порядком** реализации и не дублируют его целиком.
2. Вставляй этапы **по одному**, строго по порядку (0 → 11). Не начинай этап N+1, пока агент не отчитался по этапу N.
3. Если агент упёрся в лимит сессии посреди этапа — не переходи к следующему этапу. Вставь **тот же этап ещё раз** (текст ниже уже требует от агента сначала прочитать `docs/IMPLEMENTATION_STATUS.md` и продолжить с места остановки).
4. Каждый блок ниже самодостаточен — можно копировать целиком, включая «Базовые правила».

## ЭТАП 0 — Фундамент, окружение, схема данных, работа с секретами

Базовые правила (действуют на этом и всех следующих этапах):
- В проекте есть `docs/JANTOK_MASTER_SPEC.md` — полная спецификация v1. Перед работой прочитай в нём разделы, указанные для этого этапа, и всегда держи в силе сквозные разделы 1–6, 29, 35, 36 (приоритет решений, архитектура, границы продукта, деньги/время, модель данных, безопасность, порядок работы), даже если этап их прямо не называет.
- Никаких заглушек: TODO / `UnimplementedError` / пустой обработчик / закомментированная бизнес-логика на основном пути запрещены. Если что-то не закончить без данных от меня — см. пункт про секреты, но сама логика и код должны быть дописаны полностью.
- Любой секрет или персональные данные, которые я передам позже (номера супер-админов, ключи SMS/OTP, платёжного провайдера, Яндекс Доставки, S3, FCM, SMTP, домен/доступы сервера, реальные цены и нормы) — только через переменные окружения. Не изобретай значения и не выдавай тестовые ключи за боевые. На каждую новую такую переменную сразу добавляй запись в `docs/ENV_REQUIRED.md`: имя, зачем нужна, где используется, что конкретно мне нужно прислать и в каком формате, безопасное dev/local значение по умолчанию, если оно есть.
- Работай реальными файлами и командами в рабочей папке, не выводи код вместо реализации в чат.
- Обновляй `docs/IMPLEMENTATION_STATUS.md` и `docs/REQUIREMENTS_TRACEABILITY.md` по ходу этапа, а не только в конце.
- Если упираешься в лимит контекста/времени раньше, чем закончишь этап — не ускоряйся в ущерб качеству и не заявляй о завершении непроверенного. Останови работу на чистой границе, зафиксируй в `IMPLEMENTATION_STATUS.md` точку продолжения.
- В конце этапа — короткий отчёт на русском: что сделано, что реально проверено (команда → результат), какие переменные добавлены в `ENV_REQUIRED.md`, что не уместилось.

Задачи этого этапа (разделы мастер-спека 1–6, 29, 30, 35, 36, 41):
- Исследуй окружение (раздел 3), зафиксируй структуру `jantok-mobile/ jantok-backend/ jantok-admin/ docs/ infra/ scripts/`.
- Подними скелеты трёх приложений по стеку из раздела 4 (Flutter/Riverpod, NestJS/Prisma, Next.js), Docker Compose, Nginx, GitHub Actions — без бизнес-логики, но с реально работающим `docker compose up`, миграциями на пустую БД и CI, который проходит на пустом проекте.
- Спроектируй и накати физическую модель данных из раздела 29 (ядро: users, household, members, orders/дни, subscriptions, payments, ledger, inventory — насколько уже понятно из ТЗ; остальное будешь дополнять по ходу следующих этапов, без «одной большой миграции на всё сразу»).
- Создай `docs/ENV_REQUIRED.md` и внеси в него всё, что уже понятно на этом этапе (минимум: номера двух Super Admin, параметры БД/Redis, базовый JWT/secret для сессий).
- Создай `docs/IMPLEMENTATION_STATUS.md`, `docs/REQUIREMENTS_TRACEABILITY.md`, `docs/ARCHITECTURE.md`, `docs/ASSUMPTIONS.md` (пустые/стартовые, но реальные файлы, которые следующие этапы будут дополнять).
- README/QUICKSTART с точными командами локального запуска того, что уже есть.

Критерий готовности этапа: `docker compose up` поднимает пустые backend/db/redis, `flutter analyze` и пустой Next.js билд проходят, CI зелёный, миграции применяются на чистой БД.

## ЭТАП 1 — Авторизация, household, анкета, безопасность выбора блюд

Разделы мастер-спека: 7, 8, 9 (плюс защищённый вход сотрудников из раздела 25 — только бутстрэп двух Super Admin, без полной ролевой модели).

- SMS OTP регистрация/вход, access/refresh сессии, мультиустройственность, ротация refresh, безопасный OTP-провайдер за интерфейсом (dev inbox локально, технически запрещённый в проде bypass).
- Household на один аккаунт, профиль каждого питающегося, анкета с сохранением прогресса.
- Nutrition Engine: аллергии/ограничения реально блокируют небезопасные блюда на backend, а не только в UI.
- Бутстрэп двух Super Admin через конфигурацию/инициализацию (не в seed для прода).

Все новые секреты (OTP-провайдер, тестовые номера, номера Super Admin) — в `docs/ENV_REQUIRED.md` тем же порядком, что в Этапе 0.

Критерий готовности: реальный E2E по телефону — регистрация → OTP → анкета семьи с сохранением прогресса → повторный вход на втором устройстве без разлогина первого.

## ЭТАП 2 — Меню, подписка, cut-off, pricing

Разделы: 10, 11, 12, 13.

- Каталог блюд/альтернатив (halal, только предусмотренные позиции).
- Cut-off и финализация следующего дня как job, а не UI-таймер.
- Подписка: календарь, паузы, пропуски, участники, гости — с реальным хранением состояния, не одним полем `expires_at`.
- Pricing Engine на backend через versioned quote (раздел 6): перерасчёт при любом изменении состава до оплаты, фиксация версии правил в уже оплаченных циклах.

Критерий готовности: смена состава семьи/адреса/дня до оплаты обновляет quote; после оплаты смена настроек pricing не меняет уже купленный цикл.

## ЭТАП 9 — Локальный сквозной прогон и безопасность/эксплуатация

Разделы: 34, 35 (плюс раздел 37 — один полный E2E-сценарий из списка инвариантов, до полного набора тестов в Этапе 10).
