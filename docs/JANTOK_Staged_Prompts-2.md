# JANTOK — поэтапные промпты (полностью расписанные)

## Как этим пользоваться

1. Положи в проект файл `docs/JANTOK_MASTER_SPEC.md` (это твой `JANTOK_Codex_Full_Development_Prompt.md`) — он остаётся резервным источником правды на случай, если агенту нужны детали сверх того, что расписано в конкретном этапе ниже.
2. Каждый блок «ЭТАП N» ниже — самостоятельный, полный промпт: базовые правила + конкретные требования домена + критерий готовности. Копируй **целиком один блок** и вставляй как одно сообщение.
3. Вставляй по одному, по порядку 0 → 11. Не начинай следующий этап, пока не получил отчёт по текущему.
4. Если агент оборвался на середине этапа (упёрся в лимит сессии) — вставь **тот же этап повторно**, не следующий.

## ЭТАП 0 — Фундамент, окружение, схема данных, работа с секретами

### Базовые правила (действуют на этом и всех следующих этапах)

- Никаких заглушек: запрещены TODO, `UnimplementedError`, пустые обработчики, закомментированная бизнес-логика на основном пути. Если что-то реально нельзя закончить без данных от меня — см. правило про секреты ниже, но сама логика и код должны быть дописаны полностью, а не помечены «сделаю потом».
- Любой секрет и любые данные, которые я передам позже (номера телефонов, ключи SMS/OTP-провайдера, платёжного провайдера, Яндекс Доставки, S3/object storage, FCM, SMTP, домен/доступы сервера, реальные цены и нормы) — только через переменные окружения. Не изобретай значения, не выдавай тестовые ключи за боевые, не оставляй переменную пустой без явной фиксации. На каждую новую такую переменную сразу добавляй запись в `docs/ENV_REQUIRED.md`: имя, зачем нужна, где используется, что конкретно мне нужно прислать и в каком формате, безопасное dev/local значение по умолчанию, если оно есть.
- Работай реальными файлами и командами в рабочей папке проекта, не выводи код вместо реализации в чат.
- Обновляй `docs/IMPLEMENTATION_STATUS.md` и `docs/REQUIREMENTS_TRACEABILITY.md` по ходу этапа, а не только в конце.
- Если упираешься в лимит контекста/времени сессии раньше, чем закончишь этап — не ускоряйся в ущерб качеству и не заявляй о завершении непроверенного. Останови работу на чистой границе (рабочий закоммиченный код, актуальная документация) и зафиксируй в `IMPLEMENTATION_STATUS.md` точную точку продолжения: что сделано, что проверено, что осталось, каким шагом продолжать.
- В конце этапа — короткий отчёт на русском: что реализовано, что реально проверено (команда → результат), какие переменные добавлены в `ENV_REQUIRED.md`, что не уместилось.

### Продукт, который ты строишь (держи в голове на всех этапах)

JANTOK — сервис месячной подписки на персонализированное питание с ежедневной утренней доставкой на весь день (завтрак, обед, ужин). Расчёт на одного человека и на семью (household), у каждого члена семьи — свой профиль питания. Клиент может менять блюда из допустимых альтернатив до cut-off, убирать/добавлять ингредиенты за доплату, покупать доп. товары. Один город (Астана), одна кухня, сторонняя доставка (Яндекс), модульный монолит (не микросервисы). Полностью halal.

**Входит в v1:** мобильное приложение (iOS+Android), SMS OTP регистрация, анкета household и каждого члена семьи, nutrition-рекомендации, месячная подписка с паузами/пропусками/переносами/гостями, ежедневные заказы с выбором блюд и add-ons, оплата картой с автопродлением, возвраты по правилам, интеграция Яндекс Доставки с трекингом, полная admin-панель, кухонный модуль (production/packing/labels), склад (закупки/списания/себестоимость), отзывы/поддержка/жалобы с фото, промокоды/бонусы/referral/JANTOK CLUB, push+SMS, kk/ru/en, экспорт в Excel/CSV, RBAC/роли/audit log.

**Не входит в v1:** своя курьерская служба и приложение курьера, несколько городов, multi-kitchen, marketplace/JANTOK Market/Clean/Services, микросервисы/Kubernetes, dark mode, недельные/однодневные основные подписки, отдельный fitness-трекер.

**Денежные и временные инварианты, действующие всегда:**
- Валюта — тенге (KZT), целые единицы для денег в UI/расчётах, Decimal (не float) для количеств, себестоимости и любых промежуточных долей.
- Все даты/дедлайны считаются в единой business timezone проекта (Астана), а не в timezone устройства клиента.
- Любое число (цена, порог, дедлайн, лимит), не зафиксированное явно как утверждённое бизнес-решение ниже — настраиваемое значение в System Settings со статусом `demo/draft/approved`, а не хардкод.

### Что нужно сделать на этом этапе

1. **Исследуй окружение.** Если в папке уже есть код — не затирай его молча; зафиксируй, что уже есть, в `docs/IMPLEMENTATION_STATUS.md` перед изменениями.
2. **Архитектура и репозитории.** Модульный монолит backend (не микросервисы) — оправдан на масштабе первых 50–100 клиентов. Структура: `jantok-mobile/` (Flutter/Riverpod), `jantok-backend/` (NestJS/Prisma/PostgreSQL/Redis), `jantok-admin/` (Next.js), `docs/`, `infra/`, `scripts/`. Backend модули как отдельные папки внутри монолита: `/auth /users /households /members /questionnaires /nutrition /ingredients /allergens /meals /menus /subscriptions /pricing /orders /addons /addresses /payments /refunds /delivery /kitchen /inventory /suppliers /purchases /loyalty /referrals /promocodes /reviews /support /notifications /analytics /admin /audit /integrations /settings`.
3. **Docker Compose** поднимает PostgreSQL, Redis, object storage (S3-совместимый, напр. MinIO), backend/API, worker, admin в одной сети. Nginx конфиг с TLS termination и поддержкой WebSocket — заготовка для staging.
4. **Физическая модель данных (первый срез).** Спроектируй и накати миграциями PostgreSQL/Prisma схему для базового ядра: users, user_sessions, device_tokens, households, household_members, member_profiles. Остальные домены (nutrition, menu, subscriptions, orders, payments, loyalty, delivery, kitchen, inventory, support, system/roles/audit/settings) будут добавляться миграциями в следующих этапах — не пытайся продумать все поля сразу, но заложи стратегию soft delete, naming convention и enum-подход, которую будешь соблюдать во всех следующих миграциях.
5. **CI.** GitHub Actions с независимыми job на backend/admin/Flutter: lint/format/typecheck + миграции на чистой тестовой БД. На пустом проекте CI должен быть зелёным.
6. **Документация-скелет.** Создай реальные файлы (пусть короткие, но настоящие, не пустые заголовки): `docs/ENV_REQUIRED.md`, `docs/IMPLEMENTATION_STATUS.md`, `docs/REQUIREMENTS_TRACEABILITY.md`, `docs/ARCHITECTURE.md`, `docs/ASSUMPTIONS.md`. В `ENV_REQUIRED.md` сразу внеси то, что уже понятно: параметры БД/Redis/S3, JWT/session secret, номера двух Super Admin (пока как переменные без значений).
7. **README/QUICKSTART** с точными командами локального запуска того, что уже есть на этом этапе.

### Критерий готовности этапа
`docker compose up` поднимает пустые backend/db/redis/storage; `flutter analyze` и пустой Next.js build проходят; CI зелёный; миграции применяются на чистой БД; все пять `docs/*.md` файлов реально существуют и не пустые.

## ЭТАП 1 — Авторизация, household, анкета, безопасность выбора блюд

### Базовые правила
(те же, что в Этапе 0: никаких заглушек; секреты только через `.env` + запись в `docs/ENV_REQUIRED.md`; вести `IMPLEMENTATION_STATUS.md`/`REQUIREMENTS_TRACEABILITY.md` по ходу; при упоре в лимит сессии — чистая остановка с точкой продолжения, не имитация завершения; короткий русскоязычный отчёт в конце.)

### 1.1 Авторизация и сессии

- Регистрация и вход по номеру телефона + SMS OTP. Email и пароль клиенту не нужны. Для аккаунта обязательны имя и фамилия; остальное — в анкете.
- OTP: отправка, повторная отправка с интервалом, expiration, одноразовое использование, лимит попыток, rate limit по номеру/IP/устройству, защита от перебора. **Не возвращай OTP в API-ответе и не пиши его в production-логи.** Нормализуй номера в единый международный формат.
- Access/refresh сессии: ротация refresh token с обработкой повторного использования, logout текущего устройства, отзыв сессий. Один аккаунт работает одновременно на нескольких устройствах — вход второго взрослого не должен выбрасывать первого. Device push tokens привязаны к конкретной сессии/устройству.
- OTP-провайдер подключай через интерфейс. Локально — dev inbox/terminal sink и тестовые номера; такой режим должен быть **технически запрещён в production** (не просто "выключен настройкой по умолчанию" — реальная защита от включения в проде).
- Для сотрудников — защищённый вход и назначение прав на backend; сам факт наличия route `/admin` во фронтенде не даёт доступа. Бутстрэп **двух Super Admin** (технический основатель + отвечающий за бизнес/маркетинг) через конфигурацию/инициализацию, их реальные номера — переменные окружения (внеси в `ENV_REQUIRED.md`), не seed для production. Локально — отдельные демонстрационные учётные записи.

### 1.2 Household и анкета

- Один клиентский аккаунт владеет одним household. В household может быть 1, 2, 4 и больше участников — не ограничивай четырьмя из-за макета. У каждого участника — отдельный профиль питания.
- Onboarding называется «Анкета»: сначала состав семьи → анкеты всех питающихся → адрес и параметры доставки → рекомендации и итоговая цена. Прогресс анкеты сохраняется, при перезапуске пользователь возвращается на незавершённый шаг.
- Поля анкеты каждого участника: имя/идентификатор; дата рождения и вычисляемый возраст; пол; рост; вес; уровень активности; спорт/характер тренировок; цель (похудение/поддержание/набор веса/спорт); тип питания; предпочтения; нежелательные продукты; аллергии (справочник + свободный текст для редких случаев, с явным «нет известных аллергий» вместо тихого пропуска шага); размер порции (ручной выбор или принятие рекомендации алгоритма). Большая порция не обязана автоматически означать доплату — это правило pricing/nutrition конфигурации, не жёсткий тариф.
- Возрастные группы: **0–5, 6–12, 13–17, 18+**. У первых трёх могут отличаться нормы и цены. Категорию для уже оплаченного периода фиксируй — не меняй стоимость посреди цикла из-за дня рождения.
- Изменение профиля пересчитывает подходящие будущие рекомендации и проверяет уже запланированные блюда. Новая аллергия, затрагивающая уже зафиксированный заказ — явный конфликт + задача сотруднику, не тихая правка уже выданного production list.

### 1.3 Nutrition Engine и безопасность

- Детерминированный, тестируемый Nutrition Engine. Вход: возраст, пол, рост, вес, активность, спорт, цель, diet type, аллергии, нелюбимые продукты, предпочтения, portion preference. Выход: рекомендуемая калорийность, БЖУ, размер порции, разрешённые/заблокированные блюда, предложение меню на 30 service days.
- Все формулы/коэффициенты/диапазоны — в versioned nutrition rules (не «магические числа» в коде). Не выдавай выдуманные детские медицинские нормы за утверждённые. Нутриционные рекомендации — не диагноз и не лечебное назначение.
- Расширяемый справочник типов питания: обычное, vegetarian, halal, без рыбы, без молочного и другие. **Всё меню должно соответствовать общему halal-ограничению.**
- Аллергены проверяются **для конкретного member**, включая исходное блюдо, модификации, добавленные ингредиенты, add-ons и питание гостя. При конфликте — красное предупреждение и блокировка подтверждения **на backend** для этого человека (другому члену семьи то же блюдо может быть доступно). Скидка/отзыв/кнопка администратора не отменяют проверку аллергенов. Свободный текст аллергии, который система не может классифицировать — помечается как требующий проверки, не игнорируется молча.
- Если подходящего безопасного блюда для member нет — верни объяснимую проблему и задачу админу; не подставляй запрещённое блюдо ради заполненного календаря.

### Секреты этого этапа для `ENV_REQUIRED.md`
OTP-провайдер (или явный local-симулятор + отметка "внешняя зависимость на будущее"), тестовые номера, номера двух Super Admin.

### Критерий готовности
Реальный E2E: регистрация по телефону → OTP → анкета семьи (минимум 2 участника разного возраста, один с аллергией) с сохранением прогресса при перезапуске → повторный вход на втором устройстве без разлогина первого → аллергенное блюдо реально блокируется на backend для конкретного участника.

## ЭТАП 2 — Меню, подписка, cut-off, pricing

### Базовые правила
(как в Этапе 0/1: без заглушек; секреты в `.env` + `ENV_REQUIRED.md`; статусы вести по ходу; чистая остановка на лимите; отчёт в конце.)

### 2.1 Меню и карточки блюд

- Планируй меню на **30 service days**. Клиенту показывай 7 календарных дней вперёд с отметками пауз/пропусков; план продлевается по ходу подписки, чтобы оплаченные дни оставались обеспечены меню.
- Каждый активный member получает завтрак, обед, ужин. У каждого meal slot — рекомендованное блюдо и заранее подготовленные допустимые альтернативы. **Замена бесплатная до cut-off**, premium-замен нет. Нельзя назначить блюдо, отсутствующее в опубликованном меню нужной даты/слота.
- Карточка блюда: фото, название, kcal, белки, жиры, углеводы, вес, состав, аллергены, рейтинг, отзывы. Переводы (название/описание/состав) — kk/ru/en через локализованные данные, не одно поле на русском.
- Модификации: удаление ингредиента — только если у рецепта/ингредиента флаг customization availability; добавление — только из допустимого списка, с ценой/остатком/проверкой ограничений участника. Пересчитывай состав/граммовку/БЖУ/аллергены/стоимость через реальные recipe quantities. Разделяй "доп. ингредиент в блюде" (свой cut-off) и "самостоятельный add-on товар" (тоже свой cut-off, см. Этап 4). **Сохраняй snapshot** рецепта/порции/состава/модификаций в заказе — редактирование карточки блюда потом не меняет старую упаковку/себестоимость задним числом.

### 2.2 Cut-off и финализация следующего дня

Единый серверный `CutoffService` для mobile/admin/API/jobs/платёжных подтверждений/всех редактирований заказа. Рабочие ориентиры (хранятся в settings, эти — стартовые значения):

| Операция на завтрашний день | Начальный рабочий ориентир |
| --- | --- |
| Изменение блюда/модификаций | До 13:00 текущего дня |
| Оплата и старт подписки завтра | До 13:00 текущего дня |
| Пропуск дня | До 14:00 текущего дня |
| Изменение адреса | До 14:00 текущего дня |
| Изменение delivery slot | До 14:00 текущего дня |
| Покупка самостоятельных add-ons | До 15:00 текущего дня |
| Финальная фиксация кухни | После последнего cut-off, ориентир 15:05 |

- «До» = строго раньше дедлайна; на самой границе изменение закрыто — покрой граничными тестами. Не проверяй права на изменение только по статусу `SCHEDULED` — у разных действий разные дедлайны.
- Смена настроек не должна ретроактивно отменять уже оплаченные обязательства. Для старта завтра ориентируйся на авторитетный статус/время оплаты у провайдера (учитывая задержку webhook), не на клик клиента. После дедлайна — понятное объяснение и ближайшая доступная дата; уполномоченный админ может внести исключение с причиной/аудитом/пересчётом production-packing-stock и уведомлением, без обхода аллергенных и финансовых инвариантов.

### 2.3 Подписка, календарь, паузы, пропуски, участники, гости

- Основной цикл — **30 оплаченных service days**, не 30 календарных дней. Старт в тот же день запрещён; после cut-off первая возможная дата — минимум послезавтра (или позже по выбору клиента).
- Явная модель service-day allocation/ledger: планирование, резервирование при фиксации заказа, использование, перенос, отмена, компенсация. Рабочее допущение: день фиксируется как использованный после `DELIVERED`; проблемная доставка сохраняет резерв до административного решения (использование либо возврат/компенсация дня). Не выдавай бесконечные бесплатные дни из-за зависшего статуса.
- **Пауза**: до 30 календарных дней суммарно за цикл, несколькими периодами (лимит настраивается). Даты не пересекают уже исполненные дни. Применяется дедлайн для начала паузы ближайшего дня; исключения для уже зафиксированных заказов — только через явный override.
- **Skip**: разрешён до своего cut-off, пропущенный день переносится в конец цикла (не сгорает). Skip и пауза — разные операции с раздельными лимитами и явной документированной политикой. Повторный skip того же дня не добавляет ещё один день.
- После pause/skip пересчитывай календарное окончание, будущие заказы, recurring add-ons, прогноз производства, jobs автопродления/уведомлений. Бесплатный день от админа хранится отдельно от оплаченной стоимости (не увеличивает сумму денежного возврата).
- **Постоянный участник**, добавленный в текущий цикл: 1) создать member + анкету; 2) определить реальные оставшиеся даты с учётом cut-off; 3) рассчитать доплату через Pricing Engine — ориентир `monthly_member_price / 30 × eligible_remaining_service_days` с корректным округлением; 4) подключить только после успешной оплаты/расчёта бонусами; 5) синхронизировать конец его участия с текущим циклом household (не отдельная произвольная подписка).
- **Гость**: временное питание на 1+ выбранных дней в рамках активной подписки, со своими параметрами питания/аллергиями, отдельной оплатой, добавляется в тот же Daily Order/доставку. Не меняет постоянный состав семьи, не создаёт отдельный однодневный тариф.
- Реализуй просмотр статуса/оставшихся дней/календаря/пауз/пропусков/истории изменений/ручного продления/настройки автопродления. Исключи дублирование активных циклов/заказов при повторных/параллельных запросах с разных устройств.

### 2.4 Pricing Engine

- Расчёт из состава household, возрастных категорий, актуальных правил: цена взрослого/ребёнка по группам, семейные коэффициенты/скидки, платные ингредиенты, add-ons, гости, prorate, промокоды, оплата бонусами. Не добавляй неутверждённую доплату за большую порцию или район доставки.
- Формула: сумма стоимости участников + разрешённые доп. позиции − скидки − оплачиваемая бонусами часть = сумма к оплате деньгами. Для каждой суммы — детализация и объяснение применённых правил (возвращаемое клиенту "почему такая цена").
- Числа ~350 000 ₸/подписка и ~200 000 ₸/человек — обсуждавшиеся примеры, **не финальные цены**. Локально — явно demo pricing rules; для production цены должны быть активированной бизнес-конфигурацией, не выдумкой.
- Сохраняй неизменяемую финансовую детализацию покупки по участникам/service days/позициям — нужна для точного prorate, стоимости неиспользованного питания, частичного возврата. Не пересчитывай старый возврат по сегодняшнему прайсу.
- Раздели: состояние финансовой покупки, состояние банковской операции, состояние подписки/заказа. `Payment succeeded` ≠ `Order delivered`. Полностью бесплатная/бонусная операция должна корректно завершаться без банковского списания на ноль.

### Критерий готовности
Смена состава семьи/адреса/дня **до оплаты** обновляет quote в реальном времени с детализацией; **после оплаты** смена настроек pricing не меняет уже купленный цикл; изменение блюда/skip/pause строго блокируется на границе cut-off (проверено граничным тестом до/на/после дедлайна).

## ЭТАП 3 — Платежи, автопродление, возвраты

### Базовые правила
(как в предыдущих этапах.)

### 3.1 Платежи, сохранённые карты, чеки

- Банковская карта, оплата всего месячного цикла сразу, сохранённые способы оплаты через токенизацию провайдера, история платежей, возвраты, чеки, автосписание. **PAN/CVV не попадают в базу/логи/аналитику JANTOK** — только защищённый checkout/SDK провайдера и допустимые identifiers/tokens + маскированные metadata.
- Поставщик платежей и фискализации **не выбраны заказчиком**. Создай `PaymentProvider` и `FiscalizationProvider` как интерфейсы, полноценные локальные симуляторы и контрактные тесты. Если позже появится реальный провайдер — адаптер по его официальной документации подключается через тот же интерфейс. Зафиксируй эту внешнюю зависимость явно в `docs/ENV_REQUIRED.md` и `docs/ASSUMPTIONS.md` — остальной payment domain должен быть полностью готов уже сейчас.
- Платёжный процесс: создание intent/checkout → сохранение pending operation → подтверждение от сервера провайдера → обработка ошибок/отмены/timeout → reconciliation зависших операций → привязка к покупке → безопасный повтор. **Возврат пользователя по deep link сам по себе не подтверждает оплату.** Подписка активируется только после авторитетного подтверждения провайдера либо завершённого внутреннего расчёта бонусами.
- Webhook: проверка подлинности документированным способом провайдера, сохранение event ID и результата обработки. Повторы/события не по порядку не должны повторно активировать подписку, начислять бонусы, создавать refund или чек дважды.
- Idempotency keys, уникальные provider operation IDs, транзакционность внутренних переходов, outbox/reconciliation для внешних вызовов. После network timeout — сначала выясни результат у провайдера, не создавай второе списание с новым ID безусловно.
- Чек — отдельный жизненный цикл: ожидается → формируется → сформирован / ошибка → возвратный документ при необходимости. Квитанция симулятора явно маркирована тестовой, не называется фискальным чеком. Раздел контроля с прикреплением/регистрацией реального документа и интерфейсом будущего автоматического адаптера. Ошибка отправки чека не создаёт повторный платёж.

### 3.2 Автопродление

- Явное согласие, сохранённый token/mandate провайдера, просмотр условий следующего цикла, возможность отключить, **предварительное уведомление за 3–5 дней** (точное окно — в settings).
- Продление привязано к окончанию оплаченных service days, не к фиксированному числу месяца. Pause/skip/добавленные дни меняют ожидаемую дату продления и связанные jobs без двойных списаний.
- Перед списанием: действующий мандат, отсутствие отмены, актуальность уведомления, цена следующего цикла. Если условия изменились так, что окно уведомления не соблюдено — перенеси списание или запроси ручное подтверждение (не списывай неожиданно).
- Не допускай пересекающихся дублирующих заказов. При payment failure — не считать продление успешным, показать понятную проблему и действие повторной оплаты. Ограниченная/настраиваемая retry-политика, не бесконечные попытки.

### 3.3 Возвраты, отмены, компенсации

| Ситуация | Требуемое поведение |
| --- | --- |
| До первой доставки | 100% возврат суммы соответствующей покупки, корректное восстановление бонусной части |
| В первые 7 дней | Возврат за неиспользованную часть подписки |
| После 7 дней | Обычный добровольный возврат недоступен |
| Ошибка JANTOK, недоставка, качество | Отдельный административный процесс компенсации/возврата независимо от стандартного окна |

- Граница "первых 7 дней" не зафиксирована в исходном ТЗ точно — рабочее допущение: окно начинается с первой подтверждённой доставки и длится 7 календарных дней в business timezone. Конфигурируй это значение и покрой граничными тестами.
- Банковскую часть возвращай через провайдера в пределах реально удержанной и ещё не возвращённой суммы; бонусную — обратной ledger-операцией. Учитывай скидки, уже использованные дни, доплаты участников, add-ons, возвраты отдельных позиций.
- Проверь: частичный refund, повторный запрос, несколько refund на один платёж, pending/refund failure, повторный webhook. Лимиты сумм/прав — на backend в транзакции, с сохранением причины/actor/результата внешней операции.
- Начисленные за отменённую покупку welcome/referral/CLUB-преимущества корректируй обратными операциями (не удалением истории). Если бонусы уже потрачены — отдельное обязательство/корректировка с ограничением дальнейшего расходования по явной политике.

### Секреты этого этапа для `ENV_REQUIRED.md`
Ключи/аккаунт платёжного провайдера, ключи фискализации (или явная отметка "нет провайдера — используется симулятор, ждём решение бизнеса").

### Критерий готовности
Повторный запуск платёжного job после рестарта не списывает и не продлевает дважды; тестовый возврат (до первой доставки, в течение 7 дней, административная компенсация) корректно и по-разному меняет баланс/дни в каждом из трёх случаев; повторный webhook не создаёт дубли.

## ЭТАП 4 — Add-ons, промокоды, бонусы, referral, JANTOK CLUB

### Базовые правила
(как в предыдущих этапах.)

### 4.1 Add-ons

- Каталог: напитки, десерты, салаты, snacks, кофе, вода, фрукты и новые категории от админа. У товара: локализация, фото, описание/состав, ограничения/аллергены, цена, доступность, единица, остаток, количество.
- Разовая покупка на конкретную дату **и** recurring add-on на дни подписки. Количество x1/x2/x3+; постоянная покупка может иметь отдельную более низкую цену. Оплата деньгами, бонусами или комбинацией. Add-on включается в существующую утреннюю доставку без доплаты за район.
- Не отправляй add-ons в неоплаченные/приостановленные/пропущенные дни по ошибке. Для recurring — храни количество оплаченных/оставшихся единиц и привязку к service days; при переносе дня переноси и оплаченную единицу; отмены/частичные возвраты — явно. Не списывай стоимость повторно при регенерации календаря.
- До оплаты проверяй: add-on cut-off (см. таблицу Этапа 2 — до 15:00), действующая подписка, доступность дня, остаток. Персональный товар — связывай с member для проверки его ограничений; общий — показывай состав/риски всей семье.

### 4.2 Промокоды

- Типы: процентная скидка, фиксированная скидка в KZT, начисление бонусов — с расширяемой моделью будущих механик.
- Ограничения: срок действия, общий лимит использований, лимит на пользователя, только первая подписка, минимальная сумма, применимые товары/операции, правила совместимости.
- Порядок применения: скидки → бонусная оплата → банковский остаток. Рабочее допущение — один промокод на покупку, пока в настройках явно не разрешена совместимость нескольких. Не допускай отрицательной итоговой стоимости. Резерв использования промокода и его подтверждение переживают конкурирующий checkout и отмену оплаты.

### 4.3 Бонусный ledger

- Подтверждённые правила: **welcome bonus 10%** от первой успешной оплаты, **1 бонус = 1 ₸**, бонусы **бессрочные**, оплата бонусами до **100%** суммы при достаточном балансе.
- Рабочее уточнение базы welcome: фактически полученная денежная часть первой успешно оплаченной подписки после скидок, без повторного начисления на уже потраченные бонусы; полностью бонусная покупка не создаёт искусственную денежную базу для нового welcome bonus. Зафиксируй как настраиваемую политику (в ТЗ точная база не расписана).
- Wallet и неизменяемые транзакции: начисление, резерв, списание, снятие резерва, возврат, компенсация/сторно. Баланс может кэшироваться, но обязан воспроизводиться по ledger. Двойной запрос/два устройства/два платежа не могут потратить одни бонусы дважды. Откат — компенсирующей записью со ссылкой на исходную операцию.

### 4.4 Referral

- Персональный referral code/link, применяется при регистрации/первой покупке. **Награда начисляется только после реальной оплаты подписки приглашённым**, не после регистрации.
- Размер награды растёт с числом успешно приглашённых платящих друзей — все уровни и база процента **настраиваемые**. Пример «1 друг ≈ 2%, 3 ≈ 5%, 5 ≈ 10%» — иллюстрация, не production-дефолт.
- Начисляй награду за новое квалифицирующее событие по достигнутому tier без пересчёта всех старых наград задним числом (сделай это правило видимым в настройках/документации). Исключи self-referral, повторную квалификацию одного приглашённого, дубли webhook. Возврат исходной покупки приглашённого — корректируй последствия через ledger.
- «Оплатить 12-й месяц бонусами» = клиент сам накопил достаточно бонусов (например, приглашениями) — **не автоматический** бесплатный 12-й месяц после 11 оплат.

### 4.5 JANTOK CLUB

- Членство открывается после настраиваемого количества оплаченных циклов. Уровни/названия/пороги/бонусные коэффициенты/преимущества — через Admin Panel. Пример Member/Silver/Gold/Platinum и пороги 3/6/12/24 месяца — **иллюстрация, не утверждённая сетка**.
- Считай месяцы через квалифицирующие **оплаченные циклы по 30 service days**, не календарные месяцы существования аккаунта. Опиши влияние полного/частичного возврата — не повышай уровень за неоплаченное создание подписки, гостя или бесплатный день.
- Экран CLUB: баланс, доступные/зарезервированные бонусы, текущий уровень, история операций, приглашённые друзья, прогресс до следующего уровня, преимущества. Применение преимуществ проверяется на сервере. Историю друзей показывай без лишнего раскрытия их персональных данных.

### Секреты этого этапа
Обычно новых внешних секретов нет — только настраиваемые бизнес-параметры (%, пороги, tiers), которые вносятся в System Settings со статусом `demo/draft`, не в `ENV_REQUIRED.md`.

### Критерий готовности
Полный цикл: регистрация по реферальной ссылке → оплата приглашённым → начисление рефереру по правильному tier, без дублей при повторном webhook; покупка на 100% бонусов проходит без банковского списания; промокод + бонусы + скидка корректно применяются в правильном порядке без отрицательной суммы.

## ЭТАП 5 — Адреса, зона, слоты, Яндекс Доставка, статусы Daily Order

### Базовые правила
(как в предыдущих этапах.)

### 5.1 Адреса, зона, слоты

- Максимум **5** сохранённых адресов (настраиваемо, старт — 5). Основной адрес + пользовательские названия («Дом», «Работа» и т.п.). Поля: улица/дом, подъезд, этаж, квартира/офис, домофон, ориентиры, координаты — достаточные для доставки до двери.
- Backend-проверка зоны доставки по настраиваемой подтверждённой **геометрии** зоны Астаны, а не по строке «Астана» и не по грубому прямоугольнику. Локально — явная demo zone; production требует реально согласованной зоны. Ручной ввод адреса работает без геолокации телефона.
- Основной адрес меняем; на конкретную дату можно выбрать другой. Сохраняй address snapshot в заказе/доставке — изменение/удаление записи адреса не переписывает историю уже отправленного заказа курьеру.
- Доставка включена в цену подписки, не зависит от района внутри зоны. Три бесплатных слота: **06:00–08:00, 07:00–09:00, 08:00–10:00** (перекрытие — осознанно принято). На старте без лимита заказов на слот. Не добавляй скрытую slot fee или capacity cap без решения бизнеса. Не удаляй слот, используемый уже зафиксированным заказом, без управляемой миграции.

### 5.2 Яндекс Доставка и клиентское отслеживание

- Сторонняя Яндекс Доставка; своего courier app и оптимизатора маршрутов нет. Один household — одна доставка на день со всеми участниками/гостями/add-ons.
- `DeliveryProvider` interface: `calculateDelivery()`, `createDelivery()`, `cancelDelivery()`, `getStatus()`, `getCourier()`, `getTracking()`, `getETA()`. Yandex-адаптер использует реальные методы выбранного API/договора — изучи официальный список методов и порядок доступа перед реализацией. Наличие метода в общей документации не подтверждает его доступность по договору JANTOK в Казахстане — это проверяется отдельно и явно отражается в интеграционной конфигурации.
- Backend автоматически инициирует доставку для готового заказа с учётом выбранного окна и реальной схемы вызова провайдера. **Не вызывай курьера сразу ночью только потому что статус перешёл в READY** — readiness и время dispatch — разные условия.
- Idempotency, повторы с backoff, ограничение retries, reconciliation после timeout, сохранение provider ID и событий. У daily order — не более одной активной доставки одновременно.
- Webhook, если реально доступен по договору; иначе — polling с лимитами. Не придумывай endpoint/событие/возможность подписи, которых у провайдера нет. Явное отображение external statuses во внутреннюю модель + обработка неизвестных/запоздавших событий + защита от регресса финального состояния.
- В приложении клиента: карта/трекинг, статус, ETA, звонок курьеру (запускает системный dialer, отдельного чата с курьером нет). Если поле временно недоступно — честное состояние + fallback (tracking link/поддержка), **не генерируй правдоподобный ETA или движущуюся точку в production**. Номер курьера может быть маскированным/временным — получай заново после переназначения.
- `NO_ANSWER` и `DELIVERY_FAILED` — с понятным действием для поддержки; недоставка **не** автоматически считается доставленным питанием. Решение о повторной доставке/возврате/компенсационном дне принимает сотрудник явной операцией.

### 5.3 Daily Order и статусы

Статусная машина:

`SCHEDULED → LOCKED → IN_PRODUCTION → COOKED → PACKING → READY → DELIVERY_CREATED → COURIER_ASSIGNED → COURIER_PICKED_UP → ON_THE_WAY → ARRIVED → DELIVERED`

Дополнительные состояния: `SKIPPED`, `CANCELLED`, `DELIVERY_FAILED`, `NO_ANSWER`, `REFUNDED`.

- Финансовый refund может происходить **после** физической доставки — храни отдельное финансовое состояние и историю исполнения, не стирай факт `DELIVERED` одним полем.
- Таблица допустимых переходов: кто/что инициирует, условия, побочные эффекты, audit/event, возможность retry. Не разрешай произвольный `PATCH status`. Ручные исключения — команды с permissions и причиной.
- Daily order generator и finalization jobs — идемпотентны, переживают рестарт, корректно обрабатывают паузы/пропуски/продление/новых members/guests/оплаченность. Редактирование с двух устройств — version/optimistic concurrency, stale update не перетирает более новую оплату/изменение.

### Секреты этого этапа для `ENV_REQUIRED.md`
Аккаунт/договор/API-ключ Яндекс Доставки, точная согласованная геометрия зоны доставки (если/когда появится).

### Критерий готовности
`READY` не вызывает курьера мгновенно ночью (dispatch по расписанию слота); повторный timeout не создаёт двух активных курьеров; `NO_ANSWER`/`DELIVERY_FAILED` не помечаются как `DELIVERED`; шестой сохраняемый адрес и адрес вне зоны корректно отклоняются.

## ЭТАП 6 — Кухня и склад

### Базовые правила
(как в предыдущих этапах.)

### 6.1 Кухня, production, packing, labels

- Одна кухня (multi-kitchen не нужен). Production list агрегирует потребность по блюдам/порциям/ингредиентам — повар не читает отдельные клиентские заказы.
- Каждое блюдо имеет recipe quantities и единицы на порцию, версию рецепта, факторы выхода/потерь (при необходимости), разрешённые модификации. На дату рассчитывай количество порций и общую потребность ингредиентов (например, количество курицы = количество на порцию × число соответствующих порций, в складской единице).
- Агрегируй **отдельно** несовместимые варианты: другой размер порции, исключённый ингредиент, платная добавка, аллергенное ограничение — не объединяй обычное блюдо и его модификацию в одну неразличимую строку. Учитывай взрослых, детей, гостей, add-ons.
- Предварительный forecast и финальный production list — разные состояния. После cut-off кухня получает зафиксированную версию. Административное изменение после lock — новая ревизия/дельта, видимая сотруднику, с пересчётом складских резервов и packing tasks (не тихая правка распечатанного документа).
- Показывай план, фактический выпуск, недо/перевыпуск, ошибки, статусы «готовится/готово». Запись факта производства + stock movements — согласованно, не дублируются при повторном клике.
- Packing tasks группируются по household/заказу и member. Упаковщик видит точный состав коробок, индивидуальные изменения, add-ons; отмечает каждую позицию; завершает комплектацию. **Неполную упаковку нельзя автоматически объявить готовой к курьеру.**
- Печать этикеток: бренд, имя/идентификатор клиента/участника, дата, состав комплекта, номер заказа + маркировка индивидуальных ограничений там, где это предотвращает путаницу. Не печатать лишние данные анкеты. QR не нужен в v1. Принтер не выбран — создай печатные PDF/HTML layouts с настраиваемым размером, preview, повторной печатью, историей (не заявляй проверенную совместимость с неизвестной моделью принтера). Production list и packing list тоже должны иметь печатные/экспортируемые версии.

### 6.2 Склад, поставщики, закупки, себестоимость

- Полноценный inventory layer: ingredients (единицы, аллергены, категории, цены); фактический остаток и доступный остаток с учётом резервов; минимальные/критичные уровни; неизменяемая история движений; suppliers/purchases/purchase items с приёмкой и закупочными ценами; waste entries (количество, причина, дата, ответственный/смена); согласованные корректировки с причиной и аудитом.
- Типы движений: `PURCHASE`, `PRODUCTION`, `WASTE`, `CORRECTION`, `RETURN`, `TRANSFER`. `TRANSFER` — перемещение между местами хранения в одном контуре, не повод строить multi-kitchen архитектуру.
- Нормализуй g/kg, ml/l, штуки с допустимыми преобразованиями — не складывай граммы с миллилитрами без известного коэффициента конкретного ингредиента. Закупка → приход после подтверждённой приёмки; прогноз не списывает фактический склад; подтверждённое production → расход. Резерв и фактическое движение обрабатываются раздельно.
- Оценка запасов — взвешенная средняя стоимость при поступлении, с сохранённой стоимостью расхода и рецептурным snapshot. Считай стоимость блюда, дневного комплекта, оплаченного цикла, food cost, waste cost, gross margin воспроизводимо; разделяй предварительную и фактическую себестоимость.
- Складская корректировка/возврат не меняют прошлое бесследно. Refund клиенту сам по себе не означает физический возврат ингредиентов на склад. Исключи двойной учёт одного расхода в production и waste cost. Проверяй отрицательные остатки и конкурентное списание.

### Критерий готовности
Повторное подтверждение производства/списания не списывает ингредиенты дважды; отчёт по себестоимости не считает один waste дважды; несовместимые модификации одного блюда видны в production list отдельными строками, а не слиты в одну.

## ЭТАП 7 — Роли/права/аудит, полная Admin Panel, аналитика, настройки

### Базовые правила
(как в предыдущих этапах.)

### 7.1 Отзывы, поддержка, коммуникации

- Отзывы: рейтинг 1–5 звёзд + текстовый комментарий (без отдельных ❤️/👎). Публикуются сразу, видны другим клиентам; пользователь может удалить свой; администратор может скрыть/удалить с правом+причиной+аудитом (soft delete/история модерации). Клиент оценивает реально полученное блюдо с привязкой к своей позиции заказа (защита от накрутки). Не раскрывай публично телефон/возраст/аллергию/состав household автора.
- Поддержка: постоянные threads/messages, realtime (WebSocket/Socket.IO), история, статусы, непрочитанные, ответ сотрудника из Admin Panel, вложения-фото, звонок в поддержку. Обращение можно связать с Daily Order (причины: не привезли, опоздали, повреждено, невкусно, не то блюдо, другое + свободный комментарий; также для позитивной обратной связи). Разрыв WebSocket не теряет сообщения (сохранение в БД, client message ID/dedup, reconnect с загрузкой пропущенной истории). Авторизуй room/действие — клиент не подписывается на чужой household/thread подменой ID.
- Push и SMS: основной канал — push, SMS только для OTP/критичных auth-сценариев (email/WhatsApp не подключать). События: заказ готовится, курьер выехал, приближение доставки/ETA, меню на завтра доступно, напоминание cut-off, уведомление автопродления, результат оплаты/продления, проблема заказа/ответ поддержки. Маркетинговые push — только с согласием (раздельные сервисные/рекламные настройки), kk/ru/en шаблоны. Push payload не раскрывает медицински чувствительные сведения на экране блокировки.

- Централизуй colors/spacing/typography/radii/elevations/icons/reusable states. Без dark mode. Для food photos — только предоставленные/разрешённые изображения с fallback-состоянием при отсутствии (не битая картинка и не выдуманное фото блюда).
- Адаптация к маленьким/большим телефонам, SafeArea, клавиатуре, системному Back, увеличенному шрифту, длинным ru/kk подписям. Контраст, semantic labels, reduced-motion — не в жертву анимациям.
- Локализация kk/ru/en: mobile UI и уведомления — полностью; admin — с общей поддержкой переводов и завершёнными основными текстами. Flutter — ARB-механизм; переводимый backend-контент — translations tables. Plurals/даты/деньги/ошибки локализованы, явный fallback без внутренних translation keys в UI. Выбор языка сохраняется и переключается без переустановки; kk — основной язык бренда.

## ЭТАП 9 — Локальный сквозной прогон и безопасность/эксплуатация

### Базовые правила
(как в предыдущих этапах.)

### 9.1 Полный локальный сценарий без внешних секретов

- Docker Compose поднимает PostgreSQL/Redis/object storage/backend/worker/admin в одной сети (допустима dev-схема с приложениями на хосте и инфраструктурой в Docker).
- Рабочие scripts/Make targets: setup/start/stop/migrate/seed/verify/backup/restore. Setup проверяет зависимости, создаёт только отсутствующие local env из безопасных шаблонов, генерирует локальные случайные секреты, накатывает миграции и demo seed по явному local-флагу — **не перезаписывает** уже заполненный `.env`. Обычный `start` не сбрасывает базу.
- Для каждого внешнего сервиса — режимы `local simulator` / `provider sandbox` / `production` с проверкой конфигурации:
  - SMS → защищённый dev inbox/terminal sink с настоящими server-side OTP expiration/attempts;
  - Payment simulator → pending/success/failure/refund через тот же application service/webhook boundary, что и реальные подтверждения;
  - Delivery simulator → статусы, ETA/contact, проблемные исходы, с явной пометкой «тестовая доставка» в интерфейсе;
  - Push sink → сохраняет уведомления для просмотра без Firebase-аккаунта;
  - Receipt simulator → только явно тестовые документы;
  - Object storage → реально сохраняет вложения/изображения, переживает перезапуск контейнера.
- Симуляторы **не должны быть доступны в production routes**; backend в production отказывается стартовать с опасной demo-конфигурацией, никакого тихого fallback на fake provider при временном сбое настоящего сервиса.
- Демо-seed для полноценной проверки: два local Super Admin + сотрудники с ограниченными ролями; клиент без подписки и с незавершённой анкетой; одиночный клиент и семья с разными возрастными категориями; участник с известной аллергией + безопасные альтернативы + запрещённый вариант; блюда для трёх meal slots с разными порциями/рецептами/модификациями/переводами на полный цикл; подписки/заказы в типичных состояниях (skip/pause/add member/guest/recurring add-ons); payment/refund сценарии, bonus ledger, промокоды, квалифицированный referral, demo CLUB levels; production/packing/stock movements/supplier/purchase/waste и проблемная доставка; support thread с фото и отзывы. Seed детерминирован/привязан к управляемой бизнес-дате; реальные пользователи и секреты не попадают в репозиторий.

### 9.2 Безопасность и эксплуатация

- Backend RBAC и ownership checks для REST/WebSocket/файлов/exports. Защита OTP/sessions/cookies/tokens, CSRF при cookie-auth admin, CORS, request limits. Минимизация чувствительных данных в UI/логах. Валидация входных DTO, upload formats/sizes, контроль ID ресурсов. Секреты окружения — вне Git и client bundle. Проверка webhook и безопасная история integration events.
- Транзакционность бонусов/денежных allocations/возвратов/складских движений. Idempotency и восстановление scheduled jobs после рестарта. Soft delete с сохранением обязательной истории. Rate limits для чувствительных endpoints.
- Structured logs с correlation ID, health/readiness endpoints, контроль подключения к PostgreSQL/Redis/storage, видимость failed jobs. Различай проблему внешнего сервиса и собственную ошибку — без пустого catch, скрывающего exception.
- Backups PostgreSQL и object storage, настраиваемая retention, restore scripts, проверка восстановления на отдельном local/test окружении. Persistent volumes, graceful shutdown — обычная остановка не уничтожает volume.
- Раздельные LOCAL/STAGING/PRODUCTION: разные secrets/базы/buckets/provider modes. Никаких тестовых платежей и destructive seed на production. Dockerfiles, Compose для local/staging, Nginx с WebSocket+TLS, пример production env, процедура миграций/rollback.
- **Не покупай домен/сервер, не создавай платные договоры, не списывай реальные деньги, не отправляй реальные массовые сообщения, не вызывай реального курьера и не публикуй приложение/сайт без отдельной моей авторизации.** Это не мешает подготовить и локально проверить весь код/deployment/staging runbook.

### 9.3 Один полный сквозной E2E-сценарий

Пройди целиком на реальных API проекта (не изолированными mock widgets):
OTP → анкета семьи → рекомендации → quote → оплата → активная подписка → бесплатная замена блюда → платный add-on → cut-off → production → расход склада → packing/этикетка → одна доставка → delivered → отзыв/обращение.

Отдельно пройди: возврат/компенсацию и оплату бонусами.

### Критерий готовности
Сценарий выше проходит целиком без ручных обходов; результат зафиксирован в `docs/TEST_REPORT.md` с командой/шагами и итогом каждого шага, включая честно отмеченные проблемы.
